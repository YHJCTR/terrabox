## 二、统一实验口径

所有正式对比统一使用：

- OEA test 全量 1162 条；不再用 200 条结果作为正式主表或因果结论。
- LongCat 同一模型、同一 API 配置、同一 answer judge。
- 同一份 OEA train2000 LongCat Base rollout-derived store；各消融只改变一个机制开关。
- 同一 Docker、GPU/no-GPU 分 lane、服务锁、工具可见目录、max iterations、重试规则和
  artifact 输出规则。
- 结果按 task id 做 matched-pair 分析，并报告 task-level bootstrap 置信区间。
- train 建库和 eval 注入均不使用 `task_type`、`expected_tools`、gold tool calls、
  gold answer、task id 或 gold 派生 F1/reward。
- gold 只能用于事后评测、检索覆盖诊断、静态审计和 teacher-forced replay，不能进入
  prompt、memory、索引或 Q/N/R 更新。
- 当前完整方法不加入每一步一个 LLM checker agent；保留 deterministic verifier，
  其规则和触发情况必须写入 manifest。

## 三、为什么必须先复查已有 baseline

旧结果中“无经验的消融看起来超过多个自进化方法”不能直接解释为工程 guard 更有效，
原因是旧实验并非同一个因果实验：

1. 旧消融只跑固定 200 条，没有同子集 Base 和同版本完整方法，且不能代表 1162 条 test
   的任务分布。
2. `generic_guard_only` 和 `no_store_soft_only` 的代码边界没有被证明只差一个模块，
   可能保留了不同的提示、状态检查或执行保护。
3. 历史 baseline 的失败分母、Docker 配置、工具服务并发和 timeout 构成不一致。
4. ExpeL 使用 `metrics.f1`、`task_type` 和工具序列筛选/检索训练来源；这是 gold 派生或
   数据集标签信息，不符合当前严格 rollout-only 口径。
5. MemRL 的历史 memory 使用 `expected_tools` 和 `task_type`；其 reward 来源还需要
   继续追溯，不能把历史数字称为严格无标签结果。
6. Memento 历史结果来自本地 CaseBank-style adapter，不是官方 Memento 的完整复刻；
   本地 builder 的 reward 使用 `metrics.f1`，且旧构建可能保存 `task_type`。
7. ACE、Reflection、ExpeL、Memento 的 agent 图、planner/executor、记忆更新和 prompt
   与 OEA 的适配方式不同，不能只比较最后一个 F1 数字。
8. 工具错误、OSM timeout、感知服务冷启动、Docker 故障和参数错误可能对不同 adapter
   产生不同影响。

因此，旧 baseline 结果统一标记为 `adapted/historical`。在复查完成前，不在论文中写“工程
guard 打败了 MemRL/Memento”等结论。

## 十、Qwen3-2B SFT/RL 规划（记录，暂不启动）

### 目标与论文定位

Qwen3-2B 实验作为 ExperienceEvo 之外的第二条参数训练线：先做 LoRA SFT 冷启动，再做
基于真实工具执行的短程 GRPO。ExperienceEvo 仍以 LongCat 主结果为主；2B 结果用于证明
状态转移经验可以进一步用于小模型策略学习，并提供可复现的 SFT/RL 工程经历。不要把
LongCat 换成 2B 后的绝对差异直接解释成 ExperienceEvo 的方法增益。

建议的最小对照为：2B Base、2B SFT、2B SFT+terminal-only GRPO、2B SFT+state-transition
GRPO；若要声称二者互补，再补 2B ExperienceEvo 和 2B ExperienceEvo+RL。前四项可先在
固定 200 任务 pilot 上验证，只有 reward 稳定、工具调用没有塌缩后才扩展到 OEA test 1162。

### 奖励定义边界

论文版 reward 必须只使用任务文本、公开工具 schema、真实工具调用、observation、artifact
状态变化和可观测错误；不得使用 `expected_tools`、gold tool calls、gold answer、task_type
或 gold-derived F1。推荐记录如下形式的确定性奖励：

```text
r_t = w_exec * tool_exec_success
    + w_state * (Phi(state_{t+1}) - Phi(state_t))
    + w_recovery * failure_to_valid_recovery
    - w_cost * normalized_call_cost
r_terminal = verified_task_success - lambda * invalid_final
```

`Phi` 由产物/图层/统计结果的可验证完成度构成；恢复奖励只在失败后产生有效新状态时触发。
奖励应按轨迹长度归一化并裁剪到 `[-1, 1]`，区分参数错误、工具错误、timeout、OOM 和可恢复
失败。当前 `ppo/reward_fn.py` 的动态执行实现可作为工程骨架，但其默认 F1/顺序项属于
gold 派生信号，且没有 task-level verifier，不能原样作为正式 strict RL reward。

`https://huggingface.co/Qwen/Qwen3-1.7B`、
`https://huggingface.co/Qwen/Qwen3-4B`。正式实验前仍应在页面确认模型卡、revision 和许可信息，

### 两张 3090 的资源预算

在 24 GB 3090、Qwen3-2B、QLoRA、序列长度 4k--8k、每卡 batch 1 的假设下，两张卡足够做
pilot：

| 阶段 | 推荐 GPU 分工 | 显存和时间预算 |
|---|---|---|
| 数据准备/离线检查 | CPU | 通常小于 1 小时；主要耗时是轨迹清洗和 schema 校验 |
| 2B LoRA SFT，1 epoch | GPU0 训练，GPU1 空闲或服务 | 约 8--14 GB；2k--10k 条约 2--8 小时，14k 条约 6--14 小时 |
| 静态 reward GRPO smoke | GPU0/1 训练 | 约 12--20 GB/卡；100--300 条约 2--6 小时 |
| 真实工具动态 GRPO | GPU0 训练，GPU1 rollout/工具 | 约 16--23 GB；1k 条约 8--24 小时，主要受工具 timeout 和平均调用次数影响 |
| OEA 1162 评测 | 一张 agent GPU；感知服务需另占 lane | 约 12--48 小时；VLM/SAM 工具活跃时可能延长到 1--3 天 |

两张卡的关键限制不是 2B 权重，而是 rollout、训练和感知服务同时驻留。若 GRPO 期间还要
在 GPU 上常驻 VLM/SAM，不能默认认为两张卡有余量；应把感知服务固定到独立 lane，或先用
CPU/静态工具子集完成 reward smoke。正式启动前需记录 GPU、端口、容器和停止条件，结束后
检查并释放模型服务。

### 改用 4B 时的可行性

双 3090（每卡 24 GB）可以支撑 **4B QLoRA SFT + 小规模真实工具 GRPO pilot**，但不适合
全参数训练，也不建议一开始就跑 OEA 1162 全量。建议启用 gradient checkpointing、4-bit
量化、每卡 batch size 1，并限制 rollout 数和最大生成长度；训练、rollout 与感知服务必要时
分时运行。粗略预算如下，实际时间取决于平均轨迹长度、工具 timeout 和感知工具命中率：

| 阶段 | 双 3090 可行性 | 粗略时间/显存预算 |
|---|---|---|
| 4B QLoRA SFT（2k--10k 条，1 epoch） | 可行 | 约 4--12 小时；约 12--20 GB/卡 |
| 4B QLoRA + terminal-only GRPO（100--300 条 smoke） | 可行 | 约 3--8 小时；约 16--22 GB/卡 |
| 4B QLoRA + state-transition GRPO（200 条 pilot） | 可行但需严格限流 | 约 4--10 小时；约 18--23 GB/卡 |
| 4B 动态 GRPO（1k 条） | 可做但建议分批/分时 | 约 12--36 小时；工具服务可能成为瓶颈 |
| 4B 全参数 SFT/RL | 不建议 | 双 3090 显存和稳定性余量不足 |

因此 4B 方案的最低可行路径是“200 条 SFT → terminal-only GRPO → state-transition GRPO →
reward ablation”。只有在成功率、调用次数、恢复率和显存峰值都稳定后，才考虑扩展到更大
数据量；若同时常驻 VLM/SAM，应优先让 GPU0 训练、GPU1 做 rollout/工具，或关闭常驻并采用
call-scoped 服务。

### LongCat 与 2B 的补实验原则

是否必须补 2B ExperienceEvo，取决于论文声称：

1. 若 RL 只是独立的“小模型 tool-use RL”附加实验，LongCat ExperienceEvo 主表可以保留，
   2B 只需 Base/SFT/RL 三组，论文中明确这是不同模型规模的独立实验。
2. 若要声称“ExperienceEvo 能指导 RL”或“ExperienceEvo 与 RL 互补”，必须补同一 2B
   模型上的 Base、SFT、ExperienceEvo、RL、ExperienceEvo+RL，至少在同一 200 pilot，
   成功后再跑 1162 全量。
3. 2B ExperienceEvo 的 store 最好由相同 2B train rollout 构建，以检验模型内分布；已有
   LongCat store 可作为额外的 cross-model transfer 对照，但不能替代 2B-derived store。

推荐执行顺序：200 任务 2B SFT → terminal-only GRPO → state-transition GRPO → reward
ablation；确认成功率、ordered F1、调用次数和恢复率均有稳定变化后，再决定是否承担 2B
ExperienceEvo+RL 的 1162 全量成本。两张 3090 足够完成这条路线的 pilot，但不建议一开始就
同时跑全量 OEA、动态 GRPO 和常驻感知服务。
