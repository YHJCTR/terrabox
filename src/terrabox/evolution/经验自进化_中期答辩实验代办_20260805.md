### 当前结论

- v4 的核心收益不是让普通文本答案 `answer_acc` 大幅超过 Reflection/MemRL，而是让工具链更短、更少错、更接近 gold 顺序，并显著改善生成/展示类任务的 `answer_acc_w_gen`。
- v3 的教训是 hard answer-ready 和 synthetic final 会把工具轨迹做短，但容易过早结束，导致 answer judge 大幅下降；v4 通过软提示/软 verifier checkpoint 修复了这个问题。
- 论文表述建议：主 claim 放在“产物状态转移经验提升多工具 agent 的可执行性、轨迹可靠性和生成类任务完成度”，不要把 v4 包装成普通 answer_acc SOTA。
- 多 agent 目前只能说“代码支持可选 checker 子 agent，主表未启用”；如果答辩或论文要强调多 agent，需要下一步补 checker-on 实验。

## 实验原则

- 所有正式对比必须使用同一套代码、同一套数据、同一套工具可见目录和同一套指标脚本。
- Eval prompt 不能看到当前 eval 的 `expected_tools`、`gold_tool_calls`、`ground_truth`、task id 或历史精确路径。
- Train-derived store 只从 train/base rollout 的真实工具调用、参数和 observation 抽取经验。
- Gold replay 只作为数据可执行性审计、teacher upper bound 或诊断，不作为主方法默认经验来源。
- OOM、网络、provider、quota、context、Docker/service-health 等 infra 问题只做过滤、重试或单独记录，不更新 ExperienceEvo 风险。
- 不用 `success_rate` 作为核心正确性指标；它主要表示流程跑完，不代表答案或工具链正确。
- 正式结论必须同时报告 OEA 口径、strict 工具序列口径、行为稳定性、资源成本和 answer judge。

### P0 之后的立即补充

- LongCat answer judge 已经补完，当前结论是：Reflection `51.83%`、MemRL `51.11%`、Base `48.71%`、v3 `41.17%`；v3 的工具链更准更短，但最终答案质量下降，需要优先诊断。
- v3 诊断已经定位到两个主要风险：其一是 `answer_ready` 只根据产物类型判断“可回答”，没有检查任务语义槽位是否完整；其二是运行时 guard 在重复阻止工具后会自动拼 final answer，导致一些任务输出 observation 摘要而不是任务答案。
- 经验本身确实影响工具选择：v3 trace 中，有推荐工具的步骤里模型选择推荐工具的比例约 `87.4%`；但是当前经验粒度多为 `产物类型 -> 产物类型`，例如 `gpkg -> vector_layer -> route_dist`，还不足以判断“平均距离是否已计算”“局部属性是否已验证”“生成类最终产物是否已输出”。
- 生成类任务是最明显短板：v3 `answer_acc_w_gen=47.18%`，base `71.13%`；主要原因是 v3 容易停在中间分析工具，而没有调用最终 `draw_bboxes/add_text/plot/display` 产物工具。
- 把 category 指标拆成两套：
  - OEA Table4 包含式 category Any/Same/Unique，说明“是否覆盖到 gold 类别”。
  - 严格 category multiset P/R/F1，说明“是否少调、多调、乱调”。
- 对 v3 的 `evolution_trace` 输出单独表：store hit rate、selected-in-recommendation rate、avg selected rank、guard intervention、answer-ready intervention。

## P1：经验自进化机制消融

这些实验用来回答“产物状态转移经验到底带来了什么”。

| 优先级 | 实验 | 变量 | 预期回答 |
|---|---|---|---|
| P1 | `v3_full` vs `v3_no_store` | 是否加载经验 store | 经验库是否贡献超过 runtime guard |
| P1 | `v3_full` vs `v3_store_only` | 是否启用 hard guard | guard 是否是主要收益来源 |
| P1 | `v3_topk_1/3/5` | 每步注入经验数量 | 多经验是否稀释任务注意力 |
| P1 | `v3_train500/1000/2000` | store 训练数据规模 | 经验规模是否带来稳定收益 |
| P1 | `v3_random2000` vs `v3_coverage2000` | train subset 选择方式 | 覆盖工具顺序是否优于随机采样 |
| P1 | `v3_successful_only` vs `v3_all_rollout` | 是否蒸馏失败/低质轨迹 | 失败轨迹是否污染经验 |
| P1 | `v3_rollout_store` vs `gold_replay_store` | rollout-derived 与 teacher-derived | gold 是否只是 upper bound，不作为主方法 |
| P1 | `v3_answer_ready_off` | 关闭 answer-ready 收敛判断 | exact/ordered exact 的提升是否来自“及时停止” |
| P1 | `v3_hard_guard_off` / `v3_soft_only` | 关闭阻止类 guard，只保留提示 | 工具序列变短是否来自 hard guard |
| P1 | `v3_quse_off` | 不使用 Quse 排序，经验只做文本提示 | Q/N/R 工具排序是否真的贡献决策 |
| P1 | `v3_step_hint_off` | 只在任务开始注入，不按当前产物状态逐步检索 | 两阶段/逐步检索是否优于一次性经验注入 |
| P1 | `v3_fallback_off` | 关闭代码侧泛化 fallback | 当前提升是否被通用 fallback 放大 |
| P1 | `v3_lexical` vs `v3_hybrid_retrieval` | lexical 检索 vs 工具族/embedding 混合检索 | 检索质量是否限制经验效果 |
| P1 | `v3_short_block` vs `v3_long_block` | 控制经验注入 token 长度 | 经验文本是否稀释原任务注意力 |

### P2/P3 执行建议

- 中期前优先跑免梯度：MemRL、Reflection、ExpeL、SelfCritic、SkillRL skillbank、EarthBench 泛化和 answer judge；GraphSkillEvo/SeqGraphEvo 属于内部探索，暂不作为外部 baseline。
- RL/SFT 类方法只做“未来工作/后续计划”或很小的可行性 smoke，不放主表，避免两周内被训练成本拖死。
- 所有 baseline 都必须区分两种结果：
  - `offline tool prediction`：只预测工具序列，便宜但不能证明答案质量。
  - `live agent eval`：通过 `scripts/run_trajectory_experiment.py rollout --evolution-method ...` 真跑工具，才能进入主表。
- 如果某个 baseline 还没有接入 live prompt augmenter，则先跑 offline tool prediction 作为附录，不要和 v3 live eval 混在一个主表里。

## 答辩讲法草稿

- 传统 memory 方法多保存 episode、trajectory、reflection 或 skill。
- ExperienceEvo 保存的是任务执行中的产物状态转移：
  `当前产物 -> 下一目标产物 -> 可用工具排序 -> 参数/风险经验`。
- 在 OEA 这类地理空间多工具任务里，中间产物链比单条轨迹更可迁移：
  image、bbox、mask、gpkg、vector layer、numeric result、final answer。
- 当前 v3 现象若保持：
  - OEA 包含式指标不一定最高，因为它不强惩罚多调。
  - strict 工具序列、exact、ordered exact、重复调用、tool error 和 token 成本更能体现“少乱试、会收敛”的收益。
- 正式结论必须依赖同代码 base 和消融，不能只拿旧基线对比。
