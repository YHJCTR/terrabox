# ExperienceEvo v2：可执行产物状态转移族的离线经验自进化

> 状态：设计校正稿；v2 build / preview / 静态注入已落地，step-level retrieval、checker 和 gold replay 仍待实现。
> 日期：2026-07-31。
> 历史版本：`文档归档/20260731_整理前/EXPERIENCE_EVO_REDESIGN_PLAN.md` 保持原样，本文件不覆盖或改写它。
> 适用范围：Terrabox / OEA 的多工具地理空间 agent；第一阶段只做 **train rollout -> store -> test read-only eval** 的离线实验。

## 0. 结论先行

这个方向有用，但当前 MVP 还不能把“产物状态转移经验”作为已经成立的方法贡献。当前实现本质上仍是：从历史 rollout 归纳一批自然语言经验，在任务开始时做 lexical top-k 检索并静态注入 prompt。它已经证明链路能跑通，但还没有证明 agent 在运行时依据真实产物状态学习到“下一步应该产出什么”。

**v2 要主张的不是“保存经验而不保存轨迹”。** ExpeL、Reflexion、MemRL 等已经分别做了经验蒸馏、反思记忆和带价值选择的记忆检索。可以成立的贡献应当是下面这个完整对象：

```text
目标条件化的、可验证的产物状态转移族
  = 产物级转移契约
  + 该转移的多个工具实现策略
  + 工具执行后的局部验证和局部归因
  + 由当前真实 artifact state 驱动的两阶段选择
```

换句话说，rollout 只是证据来源，**不是记忆单元**。记忆单元是“把当前可用产物推进到目标产物”的可执行契约及其工具实现备选。

创新性判断：

- 当前静态 MVP：创新性较弱，属于经验检索 / prompt-memory 的一个变体；不能声称首创。
- 完整 v2：在地理空间多工具 agent 场景有中等偏强的系统方法创新潜力，前提是实现并实证下面四件事：转移族的原子保存、局部产物归因、运行时状态检索、同族工具选择与校验。
- “解决长尾”不是先验事实，而是 v2 的核心可检验假设：低频工具可以从同一产物转移的共享约束中获益，而不是靠重复记忆某条历史 workflow。

## 1. 要解决的问题

多工具 agent 的失败通常不是“不知道某个工具存在”，而是下列任一环节出错：

```text
不知道当前阶段应产出什么
-> 选了能返回文本但不能推进状态的工具
-> 参数没有绑定到正确的已有产物
-> 得到空的 / 不可消费的输出仍继续执行
-> 中间产物没有被下游使用
-> 用未验证值生成最终答案
```

因此，经验不应描述一整条任务轨迹，而应描述一个可复用的状态推进。例如一个 LST 任务可以被表示为：

```text
任务目标
  |
  +-- 任务和已有输入 -> 31 波段、32 波段、地表发射率
  |
  +-- 31/32 波段 + 发射率 -> LST 栅格
  |
  +-- LST 栅格 -> 高温区占比
  |
  `-- 高温区占比 -> 已验证的最终结论
```

同一 `输入产物 -> 目标产物` 可以有多个工具实现，或者同一工具在不同参数绑定下可成功或失败。v2 的粒度应同时保留这两层信息，而不是把它们拆成彼此无关的文本行。

## 2. 当前 MVP 与 v2 的边界

下表不是否定已有工作，而是说明为什么当前结果的小幅变化不能支撑强方法结论。

| 维度 | 当前 MVP | v2 的硬要求 |
|---|---|---|
| 存储单元 | 独立的 signature 行和 tool 行 | 一个完整 `TransitionFamily`，父转移与其工具子策略原子保存 |
| 语义条件 | 通常是通用签名 / 工具文本；蒸馏样本未稳定携带任务意图 | 脱敏的目标 / intent signature + 当前 typed artifact state |
| 奖励 | 一个 rollout 的 task-level F1 会复制到多个 transition | 每次工具调用依据输入绑定、输出有效、下游消费等局部证据评分 |
| 风险 | 已能过滤部分 infra error | 只对可归因的 LLM 工具使用错误更新；基建问题永不抬高 Risk |
| 选择 | `--max-groups` 独立截断 signature / tool bucket | 以 family 为预算单位，父项和至少一个工具子项不可拆开 |
| 检索 | 任务开始前一次 lexical top-k | 每轮工具选择前按实时状态选一个 family 或弃权 |
| 工具排序 | prompt 中展示局部 `Quse` 列表 | 在选定 family 内对可用候选工具全局排序，并带证据量 / 风险门控 |
| 校验 | 没有 graph/tool-loop 中的 checker | 工具返回后对低置信或异常结果做局部 checker，并产生 recovery hint |
| 可观测性 | 保存的 conversation history 会截断长 HumanMessage，不能用它证明完整注入内容 | 单独写结构化 audit sidecar，记录选择的 family、候选工具、Quse、是否采纳和 checker 结果 |

### 2.1 已审计到的 MVP 问题

截至 2026-07-29，对现有 train-store、检索和 prompt 注入代码的审计得到以下事实：

1. train-source 中有 `13,243` 条 transition，但经过当前 `max_groups=160` 的独立截断后，store 只有 `137` 条 signature 和 `23` 条 tool 条目。`116/137` 个保留下来的 signature 没有严格匹配的保留 tool child。这破坏了“先选产物转移、再在其工具中排序”的结构。
2. 原始 transition 的 reward 来自 rollout 级 `metrics.f1`，被复制给每一步。一个前面工具调用正确、但任务最后失败的 transition 会被错误记为低价值；反之亦然。这不是产物转移的局部 credit assignment。
3. `augment(question)` 只在任务开始调用一次。检索没有看到执行后的当前 artifact state，也没有真正按当前步骤重新选择经验。
4. 当前检索主要是停用词、别名和 lexical overlap。它能把高频 OSM 签名推广得过宽，例如低支持度的 `gpkg + bus_stops + parks -> route_distance` family 会被大量与路线无关的感知任务检索到。
5. 蒸馏时的 compact examples 没有稳定传入 `question` / intent；结果容易把“产物转移经验”写成通用工具说明书，而不是“在什么目标和前置状态下应该推进到什么产物”的策略。
6. 现有结果文件把 HumanMessage 序列化时截断到前 2000 字符。一次完整 ExperienceEvo prompt 的 Stage B 位于约 5,349 字符之后；因此历史 trace 中“看不到 Stage B”不能证明运行时未注入，只能说明 trace 不是足够的审计证据。
7. 静态 prompt block 约 7,544 字符并在多轮中持续携带，造成明显 token / 时间开销。历史 test-store smoke 的工具 set-F1 仅从 `0.696` 到约 `0.703`，而 success rate 略降，tokens/task 和 time/task 上升；这说明“多塞经验”不是有效路径。

这些现象支持一个具体判断：**核心方向尚未被充分实现，当前主要瓶颈是 family 完整性、局部归因和状态相关检索，而不是 LongCat 没有把经验文本写出来。**

## 3. v2 的正式对象定义

### 3.1 产物状态

不要把文件名、临时路径或工具 observation 原文当作 state。每个时刻的状态是一个规范化、可验证的 typed artifact slot 集：

```text
z_t = {
  artifact slots: [
    (role, type, producer, validation_status, usable_metadata), ...
  ],
  derived facts: [verified scalar / geometry / label ...],
  unavailable or invalid artifacts: [...]
}
```

示例：

```text
(area_boundary, gpkg_polygon, osm_gis.get_area_boundary, valid(feature_count=1))
(schools_layer, gpkg_point_layer, osm_gis.add_pois_layer, valid(nonempty))
(route_distance, numeric_distance, osm_gis.compute_route_dist, verified(unit=m))
```

`role` 和 `type` 比字面 path 更重要。任何 path、layer 名、地名、task id 和自由文本参数在离线蒸馏前都要脱敏为占位符。

### 3.2 目标和转移族

令 `g` 表示脱敏的任务意图 / 目标签名，令 `z_in`、`z_out` 分别表示当前和目标产物状态。一个经验族为：

```text
F = (intent_signature g, input_product_state z_in, target_product_state z_out,
     signature_policy, Qsig, Nsig, Rsig, tool_children[])
```

其中工具子策略为：

```text
P_u = (tool u, required_input_roles, parameter_binding_rules,
       output_contract, post_checks, downstream_consumption_rules,
       recovery, Qtool, Ntool, Rtool)
```

这一定义有三个不可省略的约束：

1. 一个 selected family 必须保留自己的 `signature_policy` 和至少一个可用 `tool_child`；不能再独立截断成孤儿父节点或孤儿工具。
2. 经验描述的是一个 **可执行且可校验的产物推进**，不是泛化 API 使用说明。
3. 一个工具 child 只是实现该转移的候选之一；它不等于完整 workflow，也不替代 agent 的最终决策。

### 3.3 推荐的 JSONL 形态

```json
{
  "family_id": "lst__bands_emissivity__to__lst_raster",
  "intent_signature": "derive_land_surface_temperature",
  "input_product_state": ["band31_raster", "band32_raster", "emissivity_raster"],
  "target_product_state": ["lst_raster"],
  "product_experience": {
    "goal": "Produce a georeferenced LST raster from the three verified inputs.",
    "preconditions": ["All three raster roles exist and share a compatible grid."],
    "output_checks": ["Output is a nonempty raster with a valid numeric range."],
    "downstream_rule": "Only use the raster for thresholding after the checks pass.",
    "q": 0.82,
    "n": 37,
    "risk": 0.08
  },
  "tool_policies": [
    {
      "tool": "earth_sci.split_window_lst",
      "parameter_binding_rules": ["band31 <- role:band31_raster", "band32 <- role:band32_raster"],
      "output_checks": ["result path exists", "raster is nonempty"],
      "recovery": "Do not threshold an unverified raster.",
      "q": 0.86,
      "n": 21,
      "risk": 0.05
    }
  ],
  "provenance_summary": {"verified_positive_events": 21, "local_failures": 2}
}
```

这里的文本仍可由 LongCat 蒸馏，但 LongCat 的输入必须包含 `intent + state roles + local evidence + constraints`，而不是只看到工具名和 observation 摘要。

## 5. 训练阶段的正确做法

### 5.1 数据和泄漏边界

正式实验应使用同一个、覆盖工具顺序的 train-2000 subset：

```text
OEA train -> coverage selection -> LongCat base rollout
                       |
                       +-- Reflection memory build
                       +-- MemRL source-memory build
                       `-- ExperienceEvo family-store build
```

覆盖采样可以参考 train 的 `expected_tools` 顺序，以保证有限 2,000 条任务尽量覆盖不同工具组合；但这份 gold 信息只能用于 **离线采样和事后评估**，不可进入：

- LongCat rollout 的 prompt；
- LongCat 蒸馏 prompt；
- ExperienceEvo store 的经验文本；
- OEA test 的 runtime 检索和排序。

这仍然是合理的离线自进化设置：agent 从自己的 train rollout、工具 observation 和局部检查中总结可复用经验；它没有直接得到真实轨迹作为答案。

### 5.2 局部 reward 和 risk

当前的任务级 F1 可保留为弱的终局辅助信号，但绝不能逐步复制。对某个 transition 的第一版局部评分可采用：

```text
r = 0.25 * target_product_completed
  + 0.20 * input_binding_ok
  + 0.20 * output_contract_valid
  + 0.20 * downstream_consumed
  + 0.15 * terminal_outcome_auxiliary
```

前四项来自 observation、artifact contract 和后续消费链；最后一项才允许使用 rollout 的终局工具分数或 answer judge。需要把每一项和证据写入 event，方便抽样审计。

只有可明确归因于 LLM 工具使用的情况才有：

```text
r = 0
risk_observed = 1
```

例如：选错工具、同类参数传反、引用不存在 path/layer/id、把空输出当成功继续下游、没有使用必需中间产物、用未验证数值作答。

以下情况只做 retry / 日志，不更新任何 `Q/N/Risk`：

```text
network / timeout / 429 / provider overload
OOM / GPU / Docker / service-health failure
context-length / framework / transient API failure
```

这条边界很重要：网络抖动、OOM 或上下文不足不能把“经验风险”抬高。

### 5.3 Q/N/Risk 更新和不确定性

保留原始设计的两层更新：

```text
Nsig  <- Nsig + 1
Qsig  <- Qsig  + alpha_sig  * (r - Qsig)
Rsig  <- Rsig  + alpha_risk * (risk_observed - Rsig)

Ntool <- Ntool + 1
Qtool <- Qtool + alpha_tool * (r - Qtool)
Rtool <- Rtool + alpha_risk * (risk_observed - Rtool)

alpha_* = alpha0 / sqrt(N + 1)
```

工具推荐保持你提出的定义：

```text
lambda = Ntool / (Ntool + k)
Quse(tool, family) = lambda * Qtool + (1 - lambda) * Qsig
```

但 `Quse` 不能单独决定排序。必须增加两个 guard：

```text
1. support / uncertainty guard：N 很小的 Q=1 只能标为“证据不足”，不能强推荐；
2. risk guard：Rtool 高于阈值时不走正常推荐，改为 warning + post-tool checker。
```

这不是改掉 `Quse`，而是防止 `N=3, Q=1` 的偶然成功压过大量证据较稳的工具。具体的阈值和置信区间应在 train split 内标定，不能用 test 调参。

### 5.4 Family-level 选择

当前按 signature 和 tool 分开截断会制造孤儿。v2 的 `max_families` 应按如下顺序执行：

```text
1. 聚合完整 family；
2. 计算 family support、局部质量、Risk、intent / artifact coverage；
3. 选择 family；
4. 对每个入选 family 保留所有合格 tool child，或按 family 内规则截断；
5. 若无合格 child，则该 family 不进入可执行 store，只进入分析库。
```

这会使“产物级经验指导工具级经验”在数据结构上成立，而非仅在 prompt 中假设它成立。

## 6. 测试阶段的正确用法

### 6.1 Stage A：先决定要推进到什么产物

输入是 `intent g + 当前 z_t`，而不是仅 task text。检索应先过滤：

```text
intent compatible
AND family input roles are present in z_t
AND family preconditions are valid
AND target output is not already satisfied
```

然后选择一个 family，或在证据不足时 **abstain**。一次注入最多给一个主 family 和一个备用 family，不再把三条互相冲突的转移一起塞给模型。

Stage A 的 prompt 应短到足以每轮重新生成：

```text
当前已验证产物：<roles>。
下一步目标：产出 <target product>。
前置条件：<short preconditions>。
完成后必须检查：<short output checks>。
```

### 6.2 Stage B：在同一 family 内选工具

只有 Stage A 选定 family 后才检索其 children。候选工具来源于当前 catalog / agent 计划；先做 schema 和 artifact-role 可用性过滤，再对剩余工具按照 `Quse`、support 和 Risk 排序。

每个工具只给一到两条可执行约束：

```text
1. <tool_a>  Quse=<...>, N=<...>, Risk=<...>
   Bind <parameter> to role:<artifact_role>; verify <output contract>.
2. <tool_b>  evidence insufficient
   Use only if <precondition>; run post-check <...>.
```

排序必须跨同一 family 的所有候选 tool child 统一计算，不能让多个 lexical top-k family 各自给一份排序后再按检索顺序拼接。

### 6.3 checker 和恢复

checker 不是每轮昂贵地重规划，而是只处理以下触发条件：

```text
低 support / 低 Quse override
高 Risk tool
输出不满足 contract
输入角色缺失、疑似参数绑定错误
输出未被下一步消费或出现重复无效调用
```

checker 输入必须是局部上下文：`family + before state + selected tool/args + observation + after state`。其输出只允许产生短的 recovery hint，不应把一个失败轨迹原样写回 prompt。

正式 OEA test 首版保持 store **read-only**。只保存 `validation_events.jsonl`，用于离线审计；online update 是下一阶段单独实验，不能与离线对比混在一起。

## 7. 和已有工作的关系，以及应当如何写创新点

### 7.1 不能声称的创新

下面这些单独拿出来都不是新的：

| 说法 | 为什么不能这样写 |
|---|---|
| “不更新模型权重、从历史经验学习” | Reflexion、ExpeL、MemRL 等均已有此范式。 |
| “把轨迹蒸馏成自然语言经验再检索” | ExpeL 已直接覆盖。 |
| “两阶段检索 + Q 值选择经验” | MemRL 明确采用先相关性过滤、再由效用 / Q 值选择的两阶段机制。 |
| “state-aware memory” | 近期工作已讨论状态感知、子任务对齐和状态迁移记录。 |
| “能够解决长尾” | 需要 head/mid/tail 和未见组合实验才能证明。 |

因此，不要写“first artifact-state memory”或“first two-stage memory retrieval”。这类绝对首创主张既不必要，也难以防御。

### 7.2 可防御的贡献表述

在 v2 被完整实现和验证后，建议将贡献写成：

```text
我们提出一种面向工具 agent 的、目标条件化的可执行产物状态转移族记忆。
它将“应当产出什么”的产物级策略，与“如何产出”的多个工具级实现
作为一个原子 family 保存；通过 artifact contract 的局部验证进行信用归因，
并在运行时基于当前真实产物状态选择转移、排序工具和触发恢复检查。
```

更具体地说，贡献由四个耦合部分构成：

1. **转移族而不是轨迹 / 独立记忆行。** 单位是 `intent + z_in -> z_out`，天然支持一个目标产物转移对应多种工具实现。
2. **artifact contract。** state 由有角色、类型和验证状态的产物构成；经验包含前置条件、输出契约和下游消费规则，而不是泛化工具说明。
3. **局部信用归因。** 对每个工具调用根据产物有效性和消费链更新，而非把终局 reward 无差别复制到所有步骤。
4. **实时状态条件化的两阶段控制。** 先选当前可执行的目标转移，再在同一 family 内对工具 policy 做风险 / 证据感知的 `Quse` 排序，并在必要时检查恢复。

这是一种 **组合型系统方法创新**，不是一个全新 RL 公式。它的价值要用“更准确地选对下一产物和工具、以更小上下文成本改善长尾组合”来证明。

### 7.3 文献定位

| 工作 | 已覆盖的能力 | v2 必须明确的差异 |
|---|---|---|
| [Reflexion](https://arxiv.org/abs/2303.11366) | 基于语言反馈的反思和 episodic memory | v2 不保存通用反思，而是以 artifact contract 定义局部、可执行的转移。 |
| [ExpeL](https://arxiv.org/abs/2308.10144) | 从训练轨迹提炼自然语言 insight / experience 并在推理时召回 | v2 的 primary unit 不是 insight 或相似轨迹，而是带父子工具策略的状态转移 family。 |
| [Voyager](https://arxiv.org/abs/2305.16291) | 可组合的可执行 skill library 和环境反馈迭代 | v2 不产生代码 skill，重点是跨工具实现共享的 typed artifact transition 与 validation。 |
| [MemRL](https://arxiv.org/abs/2601.03192) | 运行时 episodic memory 的两阶段检索和环境反馈下的 Q 值选择 | `Quse` / 两阶段检索本身不能当创新；v2 的区分点是 family 结构和 artifact-local credit。 |
| [MemToolAgent](https://arxiv.org/abs/2606.07909) | 结构化 tool memory、错误反思和动态决定检索条数 | v2 要证明它是状态推进与多工具实现选择，而非另一种错误反思 memory。 |
| [Structurally Aligned Subtask-Level Memory](https://openreview.net/forum?id=2CoRS45Ucj) | 让记忆粒度与子任务分解对齐 | v2 将粒度进一步落到可验证 artifact transition，并显式连接工具参数和输出契约。 |
| [A-TMA](https://arxiv.org/abs/2607.01935) | 状态感知记忆及当前 / 历史 / 过渡状态混淆问题 | v2 需要通过 state normalization、precondition 和 target-satisfied 检查避免过期经验误召回。 |
| [WebEvolver](https://aclanthology.org/2025.emnlp-main.454/) | 通过共同演化 world model 做 web-agent 自我改进 | v2 不建模完整环境 world model，而是学习可验证的工具-产物转移。 |
| [Q-Evolve](https://arxiv.org/abs/2606.07367) | 用过程级 critic 改善延迟 reward 的 credit assignment | 它支持“不能把终局分数复制到每一步”的判断；v2 使用的是无需参数训练的 artifact-local 归因。 |

**结论：** 截至本文件检索的近期工作，尚未发现完全等同于“目标条件化 artifact transition family + 多工具 child policy + 局部 artifact 验证归因 + 运行时状态驱动选择”这一完整组合的通用工具 agent 方法；但各个组成部分都有相近先例。因此最稳妥的表述是“提出并验证这一组合”，不是“首次提出记忆、状态或两阶段检索”。

## 8. 实验设计：如何证明它有用

### 8.1 公平口径

所有方法使用同一批 LongCat train-2000 base rollout 作为离线源：

| 方法 | 离线材料 | OEA test 时是否更新 |
|---|---|---|
| LongCat base / ReAct | 无经验库 | 否 |
| Reflection | 同一 train rollout | 否 |
| MemRL | 同一 train rollout | 否 |
| ExperienceEvo v2 | 同一 train rollout | 否 |

测试集为 OEA `1162` 条。ExperienceEvo 不得从 test rollout 构建 store；此前使用 test/base rollout 的实验只能标注为 transductive smoke / case-library diagnostics，不能作为正式结果。

### 8.2 必须先过的 P0 诊断

在重新跑 1162 条前，先完成这些低成本检验：

1. **Family 完整性：** 每个可检索 family 有 product policy 和至少一个 child；结构闭包应由存储逻辑保证。
2. **局部标注可信度：** 随机人工审计 transition event，检查 `input_binding`、`output_valid`、`downstream_consumed` 和 risk reason 是否与 trace 一致。
3. **检索相关性：** 在不向 agent 暴露 gold 的前提下，离线用 test gold 仅做诊断，报告 selected family 是否包含需要的工具 / 目标产物；同时报告 abstain，而不是强行给每个任务错误建议。
4. **使用证据：** 每次 rollout 记录 selected family、候选工具、Quse、LLM 实际选择、是否 override、checker 结论。不能再从被截断的 conversation history 猜测注入是否生效。
5. **上下文预算：** 每次只注入当前步骤需要的短 block；报告额外 input tokens / task，而不是只报告效果。

### 8.3 主实验和消融

先做约 100 条分层诊断集，确认运行时 hook 正常，再跑完整 OEA test。除常规 outcome 指标外，必须包含下列消融：

| 消融 | 回答的问题 |
|---|---|
| Static task-start retrieval | per-step state retrieval 是否真的必要？ |
| 无 intent signature | 仅 artifact type 是否会跨任务误召回？ |
| 独立 flat entries | family 原子结构是否优于当前 bucket store？ |
| 无 local credit | 局部归因是否优于复制任务级 F1？ |
| 无 Quse / Risk guard | 工具 child 排序和不确定性是否贡献效果？ |
| 无 checker / recovery | 后验校验是否减少参数和产物消费错误？ |
| 长 prompt 匹配对照 | 提升是否只是更多 token，而非方法本身？ |

### 8.4 报告指标

不能只看 tool set-F1。至少报告：

```text
任务层：answer judge、success、set/multiset F1、exact、ordered、LCS、Table4。
错误层：tool error、parameter binding error、invalid/missing artifact、重复调用、max-turn。
机制层：family coverage、family selection precision、tool-child rank/relevance、
        actual adoption、override、checker trigger、contract-valid、downstream-consumed、abstain。
泛化层：按工具频率 head/mid/tail、按未见工具组合 / 未见转移组合分组。
成本层：额外 prompt tokens、LLM calls、wall time、checker calls。
```

对“长尾”的最低证据要求是：在尾部工具或未见组合上，ExperienceEvo v2 的改善显著高于 head 部分，并且不是靠增加大量 token 或把 test case 重放出来。若只提高高频 OSM 任务，则不能把结果写成解决长尾。

## 9. 实现优先级和验收条件

### P0：下一轮全量 eval 前必须完成

1. 在 `transition_extractor.py` 中建立 typed artifact roles、输出契约、下游消费链和局部 event label；不再把 trajectory F1 复制给每个 transition。
2. 在 `distiller.py` 中按 `TransitionFamily` 聚合和选择，保留完整 parent-child 关系；把脱敏 intent / task hint 送入 LongCat。
3. 在 `store.py` 中以 family 为一等对象建立 JSONL / SQLite 索引，并支持按 `intent + current state` 检索。
4. 把 `prompt_injector.py` 改成可接收 `current_state`、候选工具和 `task_type` 的 step-level 接口；不要再只有 `augment(question)`。
5. 在 agent graph / tool loop 中接入执行前 retrieval、执行后 state update 和条件 checker。
6. 新增 `experience_evo_audit.jsonl` 一类结构化日志，记录未截断的选择和验证数据，但绝不写入 eval gold。

### P1：可控试跑

1. 用同一 train-2000 base rollout 重建 store。
2. 做 100 条分层 OEA test 诊断，人工查看 family / tool / parameter / state trace。
3. 先修正被证明的提取或检索错误，再启动 1162 全量；不要仅因 F1 小幅变化连续重跑。

### P2：正式比较

1. Base、Reflection、MemRL、ExperienceEvo v2 用同一 provider、相同 max iterations、相同 train source。
2. test 只读；online update 作为新的、单独命名的实验。
3. 先报告全量结果，再报告长尾和机制诊断；所有结论同时带成本。

## 10. 论文 / 汇报中可直接使用的表述

推荐：

```text
ExperienceEvo 将 agent rollout 视为生成证据的过程，而非直接可重放的记忆。
它把可验证的 artifact-state transition 作为经验单元，将目标产物策略和
多个工具实现策略封装为一个 transition family，并在每个决策步骤依据当前
artifact state 进行选择和局部验证。
```

避免：

```text
我们首次使用状态转移记忆。
我们首次使用两阶段检索或 Q 值选择。
不保存轨迹因此天然解决长尾。
```

更严谨的结论路径是：先证明 v2 的检索确实命中当前可执行的转移、agent 确实采纳了同族工具约束、局部验证确实减少错误；然后再看任务效果和尾部泛化是否同时改善。只有这条证据链成立，ExperienceEvo 才既有用，也足够区别于 Reflection、ExpeL 和 MemRL。
