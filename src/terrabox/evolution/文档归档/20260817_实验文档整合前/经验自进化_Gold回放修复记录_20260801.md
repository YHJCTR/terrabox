# 经验自进化 Gold 回放修复记录（2026-08-01）

本文记录本轮围绕 OEA `gold_tool_calls` 真实回放做的代码修复、验证结果和后续实验口径。
结论先行：**本轮没有改训练/测试数据本身，主要改的是 Terrabox 当前工具栈对 OEA gold 轨迹的兼容层和 gold replay 执行链路**。这样做的目的是先验证 “gold 轨迹在当前真实工具栈下是否可执行”，再决定是否能把 gold replay 当 teacher upper-bound 或经验抽取来源。

## 背景问题

之前直接按 OEA gold 跑，出现了大量 failed。这里不能马上下结论说 “gold 数据错了”，因为失败可能来自三类不同原因：

1. 当前 Terrabox 工具接口与 OEA gold 参数契约有轻微版本差异；
2. gold 轨迹里的 `gpkg_1` / `tif_1` / `img_1` 是动态产物占位符，需要按执行过程重新绑定；
3. OSM、Serper、Docker、VLM/InstructSAM 启动等基建问题会污染 replay 结果。

如果不先修这些执行链路，后续用 gold 判断数据质量、做 SFT/GRPO 或构建 gold-derived experience store 都会不可靠。

## 本轮改了什么

### 1. 新增 teacher-forced gold replay 链路

相关文件：

- `src/terrabox/evolution/experience_evo/gold_replay/replay.py`
- `src/terrabox/evolution/experience_evo/gold_replay/static_audit.py`
- `src/terrabox/evolution/experience_evo/runner.py`

新增能力：

- `gold-audit`：静态审计 `gold_tool_calls`，默认读取 live Terrabox registry，而不是旧 catalog 快照。
- `gold-replay`：不调用 actor LLM，直接按 `gold_tool_calls` 顺序执行真实 Terrabox tools。
- 支持 `--subset-file`：用 train2000 task id 过滤完整 train JSONL，但 gold calls 仍从完整 train JSONL 读取。
- 支持重复 `--task-id`：方便精确复测旧失败样本。
- 支持 `--max-transient-retries`：只重试 timeout / infra / provider transient replay 失败。
- replay 输出标准 `results/<task_id>.json`、`report.json`、`trajectories*.jsonl`，可复用现有 metrics/judge 链路。

为什么改：

- 用户想确认 “按 gold 轨迹跑是否本身就能得出正确结论”。
- 静态 schema audit 只能说明参数表面对齐，不能说明工具链真实可执行。
- teacher-forced replay 能把 actor LLM 变量拿掉，专门检查数据和工具栈。

不改会有什么问题：

- 会把 LongCat/agent 决策错误、工具链适配错误、gold 数据错误混在一起。
- gold 能不能作为经验抽取/训练 teacher 没法判断。
- 后续论文实验会被质疑：失败到底是方法问题还是数据/工具 replay 问题。

### 2. 修复 OEA 动态产物 alias 绑定

相关文件：

- `src/terrabox/evolution/experience_evo/gold_replay/replay.py`
- `src/terrabox/agent/tool_executor.py`
- `tests/test_gold_replay.py`

修复内容：

- replay 前把样本输入绑定为 `img_N` / `tif_N`。
- 每一步工具执行后，从工具返回 JSON 和 `artifact_index.json` 捕获新产物，绑定为 `gpkg_N` / `img_N` / `tif_N`。
- 兼容少量命名 GeoPackage 占位符：`marienplatz_gpkg_1`、`duomo_gpkg_1`、`gpkg_jeronimos_1` 会解析到对应的 `gpkg_1` 或当前最新 GeoPackage；`ndbi_2019` / `nbr_2020_02` 这类图层名不会被误当作 artifact alias。
- 每次重跑单条 task 前清空该 task 自己的 artifact 子目录，避免旧 `artifact_index.json` 污染 alias。
- `AgentToolExecutor` 的当前 GeoPackage 自动注入范围扩展到 `add_index_layer`、`compute_index_change`、`show_index_layer`、`display_on_map`、`display_on_geotiff`、`get_bbox_from_raster` 等 OSM/GIS 链式工具。

为什么改：

- OEA gold 里的 `gpkg_1` 不是实际路径，而是 “前序工具产物”。
- OEA test 中有少量人工命名的 gpkg handle，例如 `marienplatz_gpkg_1`、`duomo_gpkg_1`、`gpkg_jeronimos_1`；它们语义上仍然指向第一步 `GetAreaBoundary` 产物。
- 当前工具真实执行时会生成新的临时路径，必须按步骤重新解析。

不改会有什么问题：

- 会出现大量 `GeoPackage not found: gpkg_1`。
- 命名 gpkg 样本会出现 `GeoPackage not found: marienplatz_gpkg_1` 这类假失败。
- 这类失败不是 gold 轨迹错，而是 replay 适配没做动态绑定。
- 经验抽取会错误地把产物引用失败计入 “工具使用风险”。

已验证：

- `oea_test_187`、`oea_test_325`、`oea_test_556` 三条 alias 回归样本已重新 replay 通过，3/3 completed，avg F1=1.0。
- `oea_test_310`、`oea_test_556` 的 `get_area_boundary -> add_index_layer -> compute_index_change` 链路已通过，2/2 completed，avg F1=1.0。
- 命名 gpkg alias 已做函数级 smoke：`marienplatz_gpkg_1` 能解析到真实 gpkg 路径，`ndbi_2019` 保持为普通图层名。

### 3. 修复 OSM/GIS 兼容问题

相关文件：

- `src/terrabox/toolkits/osm_gis.py`
- `tests/test_osm_proxy_policy.py`

修复内容：

- `_osm_proxy_context` 删除 `requests_kwargs["timeout"]`，改用 OSMnx 的 `settings.requests_timeout`，避免 `requests.get()` 收到两个 `timeout` 参数。
- `get_area_boundary` 支持 `buffer_m > 0` 时优先用 point geocode，再 buffer 成面，适配 “地标/景点 + 半径” 这类 OEA gold。
- `add_pois_layer` 在没有 `gpkg` 但有 `area` / `place_name` 时，先创建 boundary gpkg，再继续查询 POI。
- `add_pois_layer` 的 schema 不再强制 `gpkg` 必填，因为 OEA gold 中存在 area-first 用法。

为什么改：

- OEA 的 GIS 轨迹经常把一个地标加 buffer 当作 AOI。
- 有些 gold call 从 `AddPoisLayer(area=...)` 开始，不先显式调用 `GetAreaBoundary`。
- 迁移环境中的 OSMnx timeout/proxy 配置会把可执行 gold 误打成错误。

不改会有什么问题：

- `Hopewell Rocks`、`Senso-ji Temple` 这类地标任务会大量失败。
- `requests.api.get() got multiple values for keyword argument 'timeout'` 会被误认为数据问题。
- OEA 中 area-first POI 任务无法真实 replay。

当前仍需注意：

- 某些 OSM query 仍可能因 Nominatim/Overpass 网络或地区覆盖失败而 timeout。
- 这类问题应在报告中单独归为 infra/OSM availability，不应混入 LLM 经验 risk。

### 4. 修复视觉工具兼容问题

相关文件：

- `src/terrabox/toolkits/geo_perception.py`
- `tests/test_geo_perception_count_bbox.py`

修复内容：

- `count_given_object` 支持 `bbox` / `region` / `box` 限定计数区域。
- 对 OEA 常见的全图 bbox 宽高互换做归一化：例如图像尺寸为 `(4592, 3072)`，gold 传 `(0,0,3072,4592)` 时识别为 `swapped_full_image_bbox`，实际裁剪全图而不是报错。
- 对轻微越界但仍与图像相交的 bbox 做 clamp；完全无效的 bbox 仍返回错误。
- 裁剪后调用 InstructSAM，并把返回 bbox 平移回原图坐标。
- `add_text` schema 增加 `color`、`font_size`，对齐 gold 中可能出现的标注参数。

为什么改：

- OEA gold 的 bbox 表示和当前 PIL/工具实现的宽高约定不总是完全一致。
- `oea_test_684` 旧失败就是全图 bbox 宽高互换导致的假失败。

不改会有什么问题：

- 合法的全图计数任务会被误判成 `invalid_argument`。
- 后续统计会错误地认为 gold 轨迹或 LLM 参数错，而不是工具适配缺口。

已验证：

- 新增直接 Python 断言：`(0,0,3072,4592)` 在 `(4592,3072)` 图上归一化为全图 crop。
- 真实 gold replay 复测 `oea_test_684`：completed，success=True，F1=1.0，工具序列为 `count_given_object -> count_given_object -> compute.plot`。

### 5. 修复 compute / provider / judge 边界问题

相关文件：

- `src/terrabox/toolkits/compute.py`
- `src/terrabox/agent/llm_provider.py`
- `scripts/run_trajectory_experiment.py`
- `scripts/judge_answers.py`
- `tests/test_tool_compute.py`
- `tests/test_trajectory_status_classification.py`
- `tests/test_llm_provider_retry.py`

修复内容：

- `compute.calculator` 支持 `math.floor(...)` 这类 gold 表达式。
- 外部 provider 的 402 / quota / billing / auth / 额度不足 不再按 transient retry。
- rollout saved result 中的 402/额度不足不再被 watcher 无限续跑。
- `judge_answers.py` 支持 JSONL task file，方便直接 judge `openearth/{train,test}.jsonl`。

为什么改：

- gold replay 和后续 LongCat judge 都会遇到账户额度、JSONL 输入和 math namespace 这类边界。
- 这些问题如果处理错，会造成空响应、无限 retry 或 judge 不可用。

不改会有什么问题：

- 402/额度不足会被误认为可恢复瞬时错误，浪费时间并污染日志。
- `math.floor` 这类 gold 表达式会在当前 calculator 下假失败。
- gold replay 输出无法直接接答案 judge。

### 6. 修复多流 GPU/服务钉卡问题

相关文件：

- `src/terrabox/managers/docker/*_manager.py`
- `tests/test_docker_resource_managers.py`

修复内容：

- SAM2 / RemoteSAM / RemoteCLIP / InstructSAM / Strip-RCNN / ChangeOS manager 支持环境变量覆盖端口和 GPU。
- 外部 API 三流场景可让 P0/P1 使用不同端口和不同 GPU lane，避免容器互相重建。
- VLM Docker 改为只暴露 leased GPU，并在容器内使用 `CUDA_VISIBLE_DEVICES=0`。

为什么改：

- 之前三流并行时，多个感知服务可能抢同名容器或回落到错误 GPU。
- LongCat/DeepSeek 外部 API actor 不占 agent GPU，本地 GPU 应尽量给工具服务并行使用。

不改会有什么问题：

- 三流 replay/eval 容易出现 container name conflict、CUDA OOM 或 GPU0 被误占。
- 实验看似是模型/方法失败，实际是服务调度失败。

## 对“数据能否用于 SFT / GRPO / 经验抽取”的判断

当前判断：

1. **不能直接把原始 gold 轨迹无审计地用于 SFT/GRPO**。原因不是 schema 已经错，而是必须先确认 replay observation 能支持 ground truth。
2. **rollout-derived 自进化仍然是主实验口径**：只看模型自己在 train task 上跑出的轨迹和 observation，不直接把 gold 轨迹喂给 eval agent。
3. **gold replay 可以作为 teacher upper-bound / 数据可执行性诊断 / 可选 gold-derived store**，但论文里要和主 self-evolution 结果分开报告。
4. 如果后续用 gold 做训练，建议只使用 `gold-replay completed + answer judge 正确` 的子集，不要使用未 replay 或 replay failed 的 gold。

## 使用命令参考

静态 audit：

```bash
PYTHONPATH=src python -m terrabox.evolution.experience_evo.runner gold-audit \
  --data data/oea_full_sft/openearth/test.jsonl \
  --out-dir tmp/experience_evo/gold_replay_current_verify/static_test_full_live_after_fix
```

单条 replay：

```bash
PYTHONPATH=src python -m terrabox.evolution.experience_evo.runner gold-replay \
  --data data/oea_full_sft/openearth/test.jsonl \
  --out-dir tmp/experience_evo/gold_replay_current_verify/bbox684_after_fix \
  --task-id oea_test_684 \
  --use-docker \
  --max-transient-retries 1 \
  --progress-every 1
```

全量脚本参考：

```bash
bash tmp/experience_evo/gold_replay_20260731/run_full_gold_replay_and_judge.sh
```

注意：全量脚本会启动多流工具服务，运行前应确认 GPU/容器空闲，并保留 `trap cleanup`，结束后检查 `nvidia-smi` / `docker ps` / `tmux ls`。
