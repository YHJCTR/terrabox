# 科研绘图论文内容 Prompt

> 用法：先粘贴你的通用科研绘图 prompt，保留其中的“我的论文内容”小节，然后把下面任意一个代码块粘贴到“我的论文内容”后面。下面内容不是完整绘图系统 prompt，而是给绘图模型理解论文方法、背景、机制和贡献的材料。

## Prompt 1：PromptEvo 静态行为协议自进化

```text
论文主题：PromptEvo：面向多工具 LLM Agent 的静态行为协议自进化方法。

研究背景：
多工具 LLM agent 的行为很大程度受 system prompt / behavior protocol 控制。人工写 prompt 往往只能覆盖少量显性规则，真实运行中仍会反复出现协议级失败：选错工具、漏调工具、重复调用失败工具、改写用户或上下文中的值、添加不支持的参数、错误恢复方式不当、过早终止、输出格式不稳定等。传统 trajectory memory、episodic memory、skill library 或 RAG 方法通常会把任务级经验、案例、轨迹或技能拼接进上下文，容易膨胀、过拟合具体任务，并且很难区分“应该修改静态行为规范”的问题和“应该检索任务经验”的问题。

核心问题：
如何在不微调模型、不保存任务级 workflow、不复用 gold 轨迹和历史答案的前提下，从真实 agent rollout 中自动发现静态 prompt 的通用缺陷，并把这些缺陷修补成可迁移、体量受控、可回归验证的行为协议更新。

方法概述：
PromptEvo 把 prompt 优化看成“静态行为协议”的自进化，而不是经验库检索。系统输入包括当前静态 prompt、真实 rollout traces、按任务对齐的指标结果，以及可选的真实 dev rollout runner。输出是一份新的静态 system prompt 或一组可编译的 typed protocol patches。整个过程只允许形成通用行为规则，不允许把 task id、文件路径、benchmark 名、实体名、固定答案或固定工具 workflow 写入 prompt。

Stage 1：开放式自发现改写。
系统先从真实 rollout 中采样失败轨迹和少量成功对照，把完整 trajectory 压缩成紧凑证据。LLM optimizer 只读取“原始 prompt + 采样日志”，自行诊断哪些失败属于 prompt-fixable 的协议缺口，哪些属于工具不可用、外部服务、上下文长度、runtime 或 evaluator 问题。然后它提出克制的新 prompt 候选，要求保留原 prompt 的结构、占位符、动态上下文锚点和已有有效规则，只做最小必要改动。

Stage 2：对比式二阶段修复。
在 Stage 1 之后，PromptEvo 不再单边追逐新 prompt 的失败案例，而是把 base prompt rollout 与 Stage1 prompt rollout 在相同 task 上配对比较。系统根据 success、tool F1、exact/API-name/argument、error bucket、cost 等指标差分，做 contrastive attribution：识别哪些 prompt 子句带来收益，哪些子句造成回归。更新策略是保留已验证收益，只窄修可归因的回归；如果证据主要来自工具故障、数据缺失、上下文限制或评测器错误，则不把它写成 prompt 规则。

类型化协议补丁分支：
除整段 prompt 改写外，PromptEvo 支持 proposal-format=patch，把候选更新限制为四类通用行为协议：tool_selection、argument_validation、error_recovery、termination_and_repetition。Patch compiler 会做确定性检查，拒绝任务专属信息、路径、benchmark 标识、固定答案和冲突规则；高风险补丁只记录，不默认编译；编译后必须保留原 prompt 的 placeholders 和末尾动态上下文锚点。

真实验证与接受门：
PromptEvo 的候选不能只靠静态文本分数接受。对可重跑的 adapter，系统用同一批固定 dev task 做真实 rollout 验证，并使用同一套指标比较当前 prompt 与候选 prompt。只有候选不造成关键指标显著退化并带来净收益时，才保存为 accepted prompt version；否则保留旧版本。

模块边界：
PromptEvo core 只依赖抽象接口 PromptStore、TrajectorySource、MetricProvider、RolloutRunner 和 LLMClient。不同 benchmark 或外部场景只需要实现 adapter，例如 Terrabox/OEA、API-Bank、tau2-bench、AgentDojo、ToolBench。core 不写项目路径、工具名、数据集特判或 gold workflow。

主要贡献：
1. 提出一种从真实执行证据中自发现静态 prompt 缺陷的方法，把 prompt 从人工规则升级为可迭代的行为协议。
2. 用 base-vs-stage1 的配对轨迹和指标差分做 contrastive attribution，避免只追逐单边失败案例。
3. 用 typed protocol patch 限制 prompt 更新空间，使更新更通用、更可审计、更难泄漏任务专属信息。
4. 用真实 dev rollout 作为接受门，避免仅凭 LLM 静态评分选择 prompt。
5. 与 memory / skill / RAG / trajectory replay 方法区分：PromptEvo 的输出是一份常量体量的静态行为协议，而不是随任务增长的经验上下文。

希望图中重点表达的主线：真实 rollout 证据如何被转化为通用 prompt 缺陷诊断，再经过保守改写、对比归因、协议补丁编译和真实 rollout 验证，最终形成下一版静态行为协议，并回到下一轮 agent 执行。
```

## Prompt 2：ExperienceEvo v4 产物状态转移经验自进化

```text
论文主题：ExperienceEvo v4：面向地理空间多工具 Agent 的产物状态转移经验自进化方法。

研究背景：
地理空间 AI agent 经常需要连续调用多个异构工具完成任务，例如视觉感知、目标定位、像素分割、GIS 图层构建、路径距离计算、栅格变化分析、数值计算、地图渲染和图像标注。任务执行过程中会不断产生中间产物：input image、raster、GeoPackage、vector layer、bbox、mask、count result、numeric result、map、plot、annotated image 和 final answer。普通 ReAct agent 容易在这些中间产物之间迷失，表现为多调、漏调、重复调用、使用历史路径、把失败 observation 当成功证据、在证据不足时回答，或完成了分析但没有生成用户要求的可视化产物。

核心问题：
传统经验方法多保存完整 episode、trajectory、reflection 或 skill，但地理空间多工具任务的关键可迁移知识并不是某条完整轨迹，而是“当前产物状态满足什么前提时，下一步应生成什么目标产物，哪些工具更可靠，参数应该如何绑定，输出应该如何检查，哪些错误应视为风险”。ExperienceEvo 的目标是在不微调模型、不读取 eval gold、不复用历史路径的前提下，把历史真实 rollout 转化为可迁移的产物状态转移经验，并在运行时按当前产物状态逐步引导 agent。

离线经验构建：
ExperienceEvo v4 复用 v2 的 rollout-derived transition store。经验来源是 train/base rollout 中真实发生的 conversation_history，包括 tool calls、arguments 和 observations。系统把每次工具调用抽取为 typed product transition event：input_product_state -> target_product_state。然后过滤基础设施错误，例如 timeout、429、网络、provider overload、OOM、context、Docker 或 service-health 问题，这些不提升经验风险。只有可归因的 LLM 工具使用错误才计入 risk，例如 missing required parameter、invalid argument、不存在的文件/图层/产物引用、无效 bbox 或 calculator expression。

经验单元：
ExperienceEvo 不把完整轨迹文本塞给 eval agent，而是聚合为 product-transition family。每个 family 包含 input_product_state、target_product_state、preconditions、output checks、downstream use、recovery hints 和 tool argument notes。经验分两层统计：product-level 的 Qsig/Nsig/Rsig 表示某类产物转移本身的质量、支持度和风险；tool-level 的 Qtool/Ntool/Rtool 表示具体工具策略的质量、支持度和风险。运行时用 Quse = lambda * Qtool + (1-lambda) * Qsig 做工具候选排序，其中 lambda = Ntool / (Ntool + k)。

隐私与公平约束：
ExperienceEvo 的主 store 只来自 train/base rollout 的真实工具执行，不读取当前 eval 的 expected_tools、gold answer、task id 或 gold_tool_calls。历史文件路径、地点名、layer 名和自由文本参数会脱敏为占位符；eval 时必须绑定到当前运行产生的 artifact 和 observation，不能复用历史路径。Gold replay 只可作为 teacher upper-bound 或诊断，不进入主方法默认经验库。

在线运行时机制：
在 eval 开始时，ExperienceEvo v4 根据用户任务和输入文件推断初始 product state，例如 task_request、input:image、input:raster、input:gpkg。检索器只返回 preconditions 已满足、与 query intent、输入形态和 available_tools 匹配的 transition families，避免把后置转移或错配经验塞入上下文。Agent 收到的是 soft product-transition guidance：当前产物状态、候选下一目标产物、Quse 工具排序、参数绑定提示和输出检查。每次工具 observation 返回后，Artifact State Tracker 更新 current product state，并触发 step_hint() 再检索下一步经验，形成“工具执行 -> 产物状态更新 -> 下一步经验检索”的闭环。

v4 相对 v3 的关键修正：
v3 的 hard answer-ready guard、premature-final guard 和 synthetic final 会让工具链更短，但容易过早结束，尤其伤害需要最终图、地图、标注或展示产物的生成类任务。v4 保留 product-transition store、Quse ranking 和 step-level retrieval，但默认关闭这些强制终止行为，把产物链判断改为 soft guidance。agent 仍然可以根据当前 observation 自行决定继续调用工具或输出答案。

Verifier checkpoint：
v4 引入 soft verifier checkpoint，根据任务文本和当前 product state 检查 missing evidence slots，例如 aggregate calculation、visual output、localized attribute、count result、plot artifact、segmentation evidence。verifier 只给 checklist、risk note 和 recommended focus，不强制脚本，不读取 gold，不直接替 agent 解题。v4 只保留两类可直接验证的硬约束：图片路径必须来自当前任务或当前运行产物；compute.calculator 必须使用合法单表达式。可选 LongCat checker/verifier 子 agent 可以审查当前任务、最近 observations 和候选 transition 是否足够，但默认关闭，避免正式全量评测请求量翻倍。

主要贡献：
1. 把多工具 agent 的可迁移经验从“完整轨迹记忆”重定义为“产物状态转移经验”。
2. 提出 product-level Q/N/R 与 tool-level Q/N/R 的两层经验统计，并用 Quse 组合排序当前可用工具。
3. 在运行时按 current product state 逐步检索经验，而不是任务开始时一次性注入全量经验。
4. 用 soft verifier checkpoint 替代 v3 的硬终止和 synthetic final，减少过早回答，同时保持工具链收敛能力。
5. 明确区分工具使用错误和基础设施错误，避免把 provider、Docker、网络或 GPU 问题污染为经验风险。

实验定位：
ExperienceEvo v4 的主 claim 不是普通文本 answer_acc 大幅超过所有 baseline，而是提升多工具 agent 的可执行性、工具使用可靠性、生成/展示类任务完成度和资源效率。在 OEA test 1162 条真实评测中，LongCat Base 到 ExperienceEvo v4 的代表性变化包括：success 85.54% -> 91.05%，tool F1 0.692 -> 0.764，answer_acc_w_gen 71.13% -> 77.46%，tools/task 6.42 -> 4.82，time/task 118.4s -> 88.5s；普通 answer_acc 基本持平，因此不应把 v4 表述成普通文本答案 SOTA。

希望图中重点表达的主线：历史真实 rollout 如何被抽取为产物状态转移经验，经验库如何在 eval 时根据当前产物状态逐步检索和排序工具，agent 如何通过工具执行不断更新产物状态，v4 又如何用 soft verifier checkpoint 保证“证据足够再回答、需要产物就生成产物”，而不是强制 replay 历史轨迹。
```
