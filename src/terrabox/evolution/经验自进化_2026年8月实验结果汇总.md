## 当前结论

- ExperienceEvo v3 的工具链确实更“短、准、稳”：set/multiset F1、exact、ordered exact、LCS、工具类别 F1、工具错误、重复调用、耗时和 token 成本都优于 LongCat base。
- 但 v3 的最终答案质量明显低于 base/MemRL/Reflection，尤其生成类任务 `answer_acc_w_gen` 掉得很重；这说明当前 v3 不能直接作为论文主结果收口。
- 最可能的问题不是“经验完全没用”，而是经验/guard 把 agent 推向过早收敛：工具序列接近 gold，但 final answer synthesis、生成类最后工具或必要的补充调用被压掉。
- 下一步主线应先做 v3 失败日志诊断与消融：`no_store`、`store_only`、`soft_only`、`answer_ready_off`、`quse_off`，再决定是否改 v4。
- tau2 可以继续低优先级跑，用来补非地理工具场景的数据量；OEA 仍是中期答辩主线。

## ExperienceEvo v3 失败诊断

### 经验库实际形态

- 当前 v3 使用的是 v2 store：`evolution_store/experience_evo/oea_train2000_v2_longcat_20260731`。
- store 来源是 `longcat_oea_train2000_seed42_base_nightly_20260724` 的 train2000 LongCat base rollout，不是 eval gold，也不是 eval 轨迹。
- manifest 记录：`num_events=13243`、`num_families=500`、`completed_only=false`、`provider=longcat`、`min_support=1`。
- `families_v2.jsonl` 中每条 family 是“当前产物状态 -> 目标产物状态”的经验，而不是完整轨迹。典型字段包括：
  - `input_product_state`：例如 `task_request`、`gpkg:from:osm_gis.get_area_boundary`。
  - `target_product_state`：例如 `vector_layer:from:osm_gis.add_pois_layer`、`result:from:osm_gis.compute_route_dist`。
  - `product_experience`：目标、前置条件、输出检查、下游规则、恢复建议、`q/n/risk`。
  - `tool_policies`：候选工具、输入角色、参数绑定规则、输出契约、工具级 `q/n/risk`。

示例经验块的语义大概如下：

```text
当前状态: gpkg:from:osm_gis.get_area_boundary
下一产物: vector_layer:from:osm_gis.add_pois_layer
Qsig=0.86, Nsig=69, Rsig=0.00
推荐工具: osm_gis.add_pois_layer, Quse=0.86
绑定: gpkg 必须绑定当前运行返回的 artifact；layer_name 用当前任务输出层名，并在后续完全复用。
检查: observation 必须真的产生 vector_layer:from:osm_gis.add_pois_layer；不能编造路径或 layer 名。
```

### 是否真的指导了工具轨迹

- 是，v3 经验/提示确实改变了工具选择。对 v3 eval trace 的统计显示：有推荐工具的步骤中，模型实际选择推荐工具的比例约 `87.4%`。
- 典型成功例：`oea_test_1066`，任务是给 Central Park 的每个 bar 分配最近 sports centre。v3 工具序列为 `get_area_boundary -> add_pois_layer -> add_pois_layer -> compute_route_dist`，与 expected tools 完全一致，answer judge 得分 `1.0`。
- 这解释了为什么 v3 的 strict 工具链指标明显变好：exact `52.0%` vs base `17.1%`，ordered exact `41.6%` vs base `13.7%`，tools/task `3.71` vs base `6.42`。
- 但它还不能稳定指导“正确完成任务”。经验只知道 `result:from:osm_gis.compute_route_dist` 已经存在，不知道是否已经完成“所有 pubs 和 hotels 的平均距离”、是否还需要 `compute.solver`，也不知道生成类任务是否还必须调用 `draw_bboxes/add_text/plot/display` 作为最终产物。

### 答案质量下降的直接原因

- 最大问题是 `answer_ready` 太粗：只要看到某类结果产物，例如 route distance 或 calculator result，就可能提示“Prefer writing the final answer now”。
- 运行时 guard 会阻止 answer-ready 之后的额外工具调用；同一个工具被阻止两次后，代码会直接合成 final answer，而不是把控制权交回 LLM 重新组织答案。
- 这个分支在 v3 中很伤：`final_after_answer_ready_repeated_tool` 出现 108 条，其中有 judge 分数的 99 条平均得分约 `0.032`。
- 失败例 `oea_test_1003`：expected tools 是 `instructsam -> calculator -> region_attribute_description`，v3 在 `calculator` 后认为 computed scalar 已足够，阻止了 `region_attribute_description`，最后输出原始检测 JSON 和数值，judge 得分 `0`。
- 失败例 `oea_test_1087`：expected tools 还需要 `compute.solver` 算平均距离，v3 在 `compute_route_dist` 后认为 route/distance result 已足够，阻止了 `compute.calculator/solver`，最后只列距离、不算 average，judge 得分 `0`。

### 生成类任务为什么掉得更重

- OEA 的生成类任务看最终生成/显示工具是否匹配并成功，不走 LLM judge。
- v3 生成类 `answer_acc_w_gen=47.18%`，base 为 `71.13%`；v3 只有 `67/142` 条生成任务最后工具匹配成功，base 是 `101/142`。
- v3 常把中间分析工具当成终点，例如最后停在 `osm_gis.compute_index_change`、`geo_perception.region_attribute_description`、`compute.calculator`，而不是最终要求的 `draw_bboxes/add_text/compute.plot/display_on_map/show_index_layer/display_on_geotiff`。
- 因此 v3 当前不是“经验没用”，而是“产物转移经验 + 过强运行时收敛”把工具链剪短了；剪短对 strict exact 有利，但对 final answer 和生成产物不一定有利。

### 代码层面的可疑位置

- `src/terrabox/evolution/experience_evo/v3/runtime.py`：`step_hint()` 在检测到 `_answer_ready_reason(...)` 后直接输出 `Answer-ready signal`。
- `src/terrabox/agent/eval_modes/common.py`：answer-ready 后若模型继续调工具，会触发 `blocked_extra_tool`；重复后进入 `final_after_answer_ready_repeated_tool`，用最近 observation summary 拼 final answer。
- `src/terrabox/evolution/experience_evo/v3/runtime.py`：`guard_tool_call()` 中有大量 task-profile hard guard，当前 v3 full 的收益混合了“经验 store”和“代码侧启发式 guard”，必须用 `store_only/no_store/soft_only` 拆开。

### 下一步建议

- 不建议立刻再跑 v3 full 全量；先做小改和消融，否则会继续浪费 LongCat 时间。
- v4/修正版优先改三点：关闭代码自动合成 final answer；生成类任务在最终展示/标注/绘图产物出现前禁止 answer-ready；把 hard guard 改成软提示或只在明显 schema 错误时阻止。
- 消融最小队列：`answer_ready_off`、`store_only`、`soft_only/hard_guard_off`、`no_store`，先跑固定 100/200 subset + answer judge，确认方向后再跑 1162 全量。
