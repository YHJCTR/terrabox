## 2. 一句话理解这个方法

本文设计的方法可以概括为：

> **普通 GRPO 只知道整条轨迹最终好不好；产物来源感知 GRPO 进一步判断每一次工具调用产生的产物是否来源正确、是否满足语义约束、是否被后续步骤正确使用，然后把信用分配给对应的工具调用。**

方法暂定名称：

> **Artifact-Provenance-Aware Credit Assignment for Agentic Tool Use**

中文名称：

> **面向产物来源约束的工具调用信用分配方法**

这里的“产物”包括：文件、图层、mask、表格、GeoPackage、统计结果以及工具返回的结构化对象。

## 3. 为什么需要这个方法

假设用户要求：

```text
比较灾前和灾后建筑变化，并统计变化面积。
```

一个合理的工具链可能是：

```text
灾前影像 -> 灾前建筑分割 -> 灾后影像 -> 灾后建筑分割 -> 变化计算 -> 面积统计
```

但是模型也可能生成下面的轨迹：

```text
灾前影像 -> 分割成功 -> 把灾前 mask 误传给灾后变化计算 -> 工具仍然返回 success
```

从工具执行层面看，最后一个工具可能没有报错；但从任务语义看，它消费了错误时间的产物。

因此需要区分三件事：

1. 工具是否执行成功；
2. 输入产物是否绑定正确；
3. 输出产物是否适合后续任务。

普通的“工具成功奖励”通常只能看到第 1 点，本文方法重点补充第 2、3 点。

## 4. 先理解普通 GRPO

### 4.1 普通 GRPO 做什么

对于同一个任务，模型采样多条完整轨迹：

```text
同一个任务
  -> 轨迹 1
  -> 轨迹 2
  -> 轨迹 3
  -> 轨迹 4
```

每条轨迹最终得到一个总 reward。例如：

```text
轨迹 1: 0.8
轨迹 2: 0.2
轨迹 3: 0.7
轨迹 4: 0.1
```

GRPO 会在同一组轨迹中比较相对好坏。一个简化的组内优势为：

\[
A_i = \frac{R_i-\operatorname{mean}(R_1,\ldots,R_G)}
{\operatorname{std}(R_1,\ldots,R_G)+\epsilon}.
\]

如果轨迹 1 的 reward 高于组平均值，就提高它出现过的回答模式概率；如果轨迹 4 的 reward 较低，就降低对应模式概率。

### 4.2 普通 GRPO 的问题

普通 GRPO 往往把同一条轨迹的优势广播给整段 assistant 输出：

```text
调用分割工具 -> 绑定影像 -> 计算面积 -> 最终回答
       A              A          A          A
```

如果中间只有“绑定影像”这一步错了，前面正确的分割动作和后面正确的恢复动作也可能收到同样的负向信号。

这就是长链路工具任务中的 **credit assignment problem（信用分配问题）**。

## 5. 我们设计的方法怎么做

本文方法仍然使用 GRPO 的组内采样和策略更新，但增加四个步骤。

### 5.1 建立产物依赖图

每个工具调用都记录：

- 调用了什么工具；
- 消费了哪些输入产物；
- 生成了哪些输出产物；
- 产物由哪个工具生成；
- 产物对应的对象、时间、单位和 CRS；
- 产物是否被后续步骤使用。

例如：

```text
灾后影像
   |
   v
建筑分割工具
   |
   v
灾后建筑 mask
   |
   v
变化计算工具
```

这张图的作用不是预测答案，而是记录“当前动作到底消费了什么、产生了什么”。

### 5.2 为每个工具动作计算局部信用

对第 \(t\) 次工具调用计算局部信用：

\[
c_{i,t} = w_s S_{i,t} + w_o O_{i,t} + w_p P_{i,t} - w_n N_{i,t}.
\]

其中：

- \(S_{i,t}\)：输入产物来源是否正确；
- \(O_{i,t}\)：输出是否满足工具的输出契约；
- \(P_{i,t}\)：输出是否被后续步骤正确消费；
- \(N_{i,t}\)：错误绑定、无效重复、空输出或负迁移惩罚。

这里的局部信用不要求知道数据集的 gold tool sequence。它主要使用真实 rollout 中可观察的工具结果、产物状态和执行错误。

### 5.3 在相同前缀下比较动作

如果几条轨迹在前面已经产生了相同或相近的产物状态，就比较它们在这个状态下选择的下一步动作。

设同一前缀下有若干候选动作，动作收益为 \(Y\)，则局部相对收益可以写成：

\[
D_{i,t} = Y_{i,t} - \operatorname{mean}(Y_{\text{同前缀的其他候选}}).
\]

直观理解：

```text
已有同一个灾后 mask
  -> 动作 A：直接统计面积，得到有效结果
  -> 动作 B：把 mask 传给不兼容工具，产生错误
```

与其只比较两条完整长轨迹，不如直接比较在这个中间状态下哪个下一步更好。

### 5.4 将信用对齐到对应 token

最终的动作级优势可以写成：

\[
\widetilde A_{i,t}
= (1-\lambda c_{i,t})A_i
 + \lambda c_{i,t}
 \operatorname{clip}(D_{i,t}/s,-a_{\max},a_{\max}).
\]

含义是：

- 保留整条轨迹的 GRPO 优势 \(A_i\)；
- 如果局部产物检查可信，就加入动作级信用；
- 只把这次工具调用对应的优势传给对应 assistant token。

示意如下：

```text
普通 GRPO：
工具调用 1   工具调用 2   工具调用 3   最终回答
    A             A             A           A

本文方法：
工具调用 1   工具调用 2   工具调用 3   最终回答
  A+delta1     A+delta2     A+delta3       A
```

system prompt、user prompt 和工具 observation 不参与 policy loss；它们只用于构造当前上下文和产物状态。

## 6. 这不是简单的 reward shaping

需要严格区分两个版本。

### 6.1 只把步骤分数相加

如果做法是：

```text
每一步得到一个分数
  -> 把所有分数相加
  -> 得到整条轨迹的一个 reward
  -> 仍然使用普通 GRPO
```

那么它只是 **reward shaping**，算法主体仍然是普通 GRPO。

### 6.2 真正的方案 A

只有完成下面这条链路，才可以称为本文方法：

```text
识别工具动作边界
  -> 构建产物依赖关系
  -> 审核来源、语义绑定和后续消费
  -> 计算动作级信用
  -> 将信用对齐到对应 assistant token
  -> 计算动作级优势并更新策略
```

因此，它的关键创新不在于“使用了步骤奖励”，而在于：

> **把产物来源和语义绑定证据接入工具动作级信用分配。**

## 7. 没有 gold tool sequence 时能不能做

可以，但方法的目标需要表述准确。

在严格无标签的 ExperienceEvo 场景中，不能直接知道：

```text
模型是否选择了数据集标注的唯一正确工具
```

因此不能把 `expected_tools` 直接送进在线 reward。

可以使用的无标签信号包括：

- 工具是否存在、参数是否符合 schema；
- 工具是否执行成功；
- 是否生成有效产物；
- 输入产物来源是否可追溯；
- 对象、时间、单位、CRS 是否冲突；
- 输出是否满足下游工具的输入契约；
- 产物是否被正确消费；
- 是否出现重复、空输出、错误循环和过早结束。

如果两个工具都能产生满足契约的有效结果，就不应该仅因为工具名称不同而惩罚模型。此时应将它们视为同一功能等价类。

因此，方法的准确表述是：

> **学习工具动作是否满足当前产物状态和任务语义约束，而不是监督模型复现某条 gold 工具序列。**

`expected_tools`、gold answer 和 Tool F1 只能用于实验结束后的独立评测与误差诊断。

## 8. 它属于哪个 RL 流派

本文方法的分类如下：

- **On-policy RL**：训练时由当前策略在线采样真实工具轨迹；
- **Policy-gradient / REINFORCE-style**：通过 reward 或 advantage 更新策略概率；
- **GRPO family**：仍然使用同一任务多条 rollout 的组内相对比较；
- **Structured/action-level credit assignment**：优势不再只停留在整条 episode，而是细化到工具动作；
- **Local/counterfactual comparison**：在相同或相近产物前缀下比较不同下一步动作。

它不是：

- Q-learning；
- offline RL；
- value-based RL；
- 单独提出的通用 step reward；
- 当前已经完成的 RL 实验。

## 9. 和 GSPO、GDPO 的关系

三者修改的是不同层面：

| 方法 | 主要改动位置 | 解决的问题 |
|---|---|---|
| GRPO | 组内相对优势 | 不使用 value model 的在线策略优化 |
| GSPO | importance ratio / clipping | 长序列 token ratio 与 sequence reward 不匹配 |
| GDPO | 多 reward 的归一化 | 多个 reward 维度合并后优势被稀释或塌缩 |
| 本文方法 | 动作级信用与 token 对齐 | 工具调用成功但产物绑定错误、长链路错误难归因 |

因此，本文方法原则上可以和 GSPO 或 GDPO 组合，但不建议第一版同时修改三处。合理的实验顺序是：

1. 标准 GRPO；
2. 多 reward + 标准 GRPO，作为 reward-shaping baseline；
3. GDPO-style 多 reward 独立归一化；
4. 本文的产物来源动作级信用；
5. 最后再尝试 GSPO 的 sequence-level ratio。

## 10. 当前实验和本文方法的关系

当前已经完成的 Qwen3B Pure GRPO 实验属于：

```text
真实工具 rollout
  -> episode-level reward
  -> 组内优势
  -> LoRA 更新
```

它没有完成：

- 产物依赖图传递到 trainer；
- 工具调用 span 对齐；
- 动作级 advantage；
- 同前缀候选动作分组；
- 产物来源约束的 token-level policy loss。

当前 ExperienceEvo Boundary v1 也不是本文方法。Boundary v1 是运行时经验边界过滤：

```text
检索经验
  -> 检查边界条件
  -> 满足条件才注入
  -> 否则回退 ReAct
```

它不更新模型参数。

所以不能把目前已有的 Qwen3B GRPO 结果直接写成“本文 RL 方法已经验证”。目前只能说：

> 已完成标准 GRPO 与 ExperienceEvo 运行时增强实验；产物来源感知 GRPO 是下一阶段的算法设计。

## 11. 实现需要修改什么

如果真正实现，需要在 veRL 训练链路中增加以下字段和逻辑：

1. rollout 侧记录每个 tool call 的起止 token span；
2. 记录该动作消费的产物和生成的产物；
3. 记录 schema、执行、来源、下游消费和错误检查结果；
4. 将动作元数据与同一 rollout 的 response tokens 一起传给 trainer；
5. 按动作或短分支计算局部收益；
6. 构造逐动作 advantage；
7. 将动作级 advantage 映射回 assistant token；
8. 保留 assistant mask，排除 system、user 和 tool observation；
9. 加入断点续跑、局部信用日志和消融开关。

推荐的独立目录结构：

```text
src/terrabox/evolution/
  experience_evo_rl/              # 现有标准 GRPO / 经验增强 RL
  artifact_credit_rl/              # 本文方案 A
    rollout_metadata.py
    provenance_checker.py
    local_credit.py
    advantage.py
    runner.py
    README.md
```

不要把方案 A 的 reward 或 advantage 静默写入公共 `rewards.py`，否则 Pure GRPO baseline 会被污染，无法公平对比。

## 12. 推荐的最小消融实验

至少需要以下五组：

| 实验 | 内容 | 作用 |
|---|---|---|
| A0 | 标准 GRPO + episode reward | 基础 RL 对照 |
| A1 | 可验证多 reward + 标准 GRPO | 判断单纯 reward shaping 是否足够 |
| A2 | A1 + 产物来源检查 | 判断来源约束是否有效 |
| A3 | A2 + 动作级信用对齐 | 验证本文核心机制 |
| A4 | A3 + ExperienceEvo | 验证经验库与动作级 RL 的组合 |

除 Success 和 Tool F1 外，还应报告：

- 产物绑定违规率；
- 工具错误率；
- 缺失工具率；
- 冗余调用率；
- 过早结束率；
- 恢复成功率；
- 未见产物组合上的泛化；
- 每个成功任务的 token 和工具调用成本。

## 13. 简历写法

### 13.1 当前可以安全使用的“设计版”写法

> **产物来源约束的工具调用信用分配：**针对多轮地理空间 Agent 中“工具执行成功但输入文件、图层或时间状态绑定错误”难以归因的问题，提出产物来源感知的 GRPO 信用分配方法，构建产物依赖图并联合验证输入来源、输出契约和下游消费关系，实现局部信用向对应工具调用 token 的精细对齐。

### 13.2 如果完成实现但还没有稳定结果

> **产物来源感知 GRPO：**针对整轨迹奖励难以定位长链路工具任务中具体错误动作的问题，提出融合产物语义绑定的动作级信用分配机制，实现对文件/图层/对象/时间/单位等来源约束的显式检查，并将局部收益映射至对应 assistant token。

### 13.3 只有完成正式消融后才能使用的写法

> **产物来源感知的 Agentic RL：**针对真实工具任务中“调用成功但产物来源错误”与“整条轨迹奖励难以进行信用归因”的问题，提出产物来源约束的动作级信用分配方法，构建产物依赖图并结合工具执行、来源绑定和下游消费验证生成局部优势，实现对应工具 token 的定向策略更新；通过标准 GRPO、过程奖励和动作级信用分配消融，提升多步工具链的产物绑定准确率与未见组合泛化能力。

### 13.4 当前不应写的表述

以下说法目前证据不足：

- “首次提出步骤级 GRPO”；
- “首次提出工具调用信用分配”；
- “已经证明动作级优势优于普通 GRPO”；
- “当前 Qwen3B GRPO 实验验证了本文方案”；
- “工具选择准确率提升”，除非有统一口径、独立评测和对应结果。

## 14. 最终定位

当前最稳妥的科研定位是：

> **ExperienceEvo 负责从真实工具轨迹中复用产物状态转移经验；产物来源感知 GRPO 进一步判断哪些工具动作值得被强化，并将可验证的产物语义证据用于动作级信用分配。**

这个方向不是重新发明 GRPO，也不是简单增加几个步骤奖励，而是把地理空间工具任务中特有的“产物来源、语义绑定和下游消费”接入已有的 Agentic RL 信用分配框架。

目前它仍属于待实现、待验证的方法设计。正式论文或简历中应根据实现和消融完成情况选择对应强度的表述。
