# ExperienceEvo 项目中的两种 GRPO 方法：对比与简历写法

> 文档目的：明确区分已经完成的 Qwen2.5-3B 标准 GRPO 实验与当前设计中的产物来源感知 GRPO，避免在简历或答辩中混淆“已验证结果”和“待验证算法”。
>
> 更新时间：2026-09-20

## 1. 先给结论

项目中目前有两层内容：

1. **已经完成的标准 GRPO**：使用真实工具 rollout，计算整条轨迹的 episode reward 和组内优势，再更新 LoRA/QLoRA；这是当前已有的 Qwen3B GRPO 实验。
2. **正在设计的产物来源感知 GRPO**：保留 GRPO 的组内比较，但进一步把产物来源、语义绑定和下游消费关系转化为工具动作级信用，并对齐到对应工具调用 token；该方法尚未完成 veRL 实现和正式消融。

最重要的区别是：

```text
标准 GRPO：一条完整轨迹一个优势，整段 assistant 输出共享
当前方法：一条完整轨迹仍有总体优势，但每个工具动作还有局部优势
```

## 2. 已完成：标准 GRPO 方法

### 2.1 方法流程

当前 Qwen2.5-3B Pure GRPO 的基本流程是：

```text
任务 prompt
  -> 当前策略采样 G 条完整工具轨迹
  -> 真实执行 Terrabox 工具
  -> 每条轨迹得到一个总 reward
  -> 同组轨迹之间做相对比较
  -> 得到 episode-level advantage
  -> 将优势用于 assistant response token
  -> 更新 LoRA/QLoRA 参数
```

对同一任务采样的第 \(i\) 条轨迹，设总 reward 为 \(R_i\)，标准化后的组内优势可以简化表示为：

\[
A_i = \frac{R_i-\operatorname{mean}(R_1,\ldots,R_G)}
{\operatorname{std}(R_1,\ldots,R_G)+\epsilon}.
\]

如果一条轨迹的 reward 高于同组平均值，就提高这条轨迹中生成模式的概率；如果低于平均值，就降低对应概率。

### 2.2 当前实现的特点

- 使用真实工具环境进行 online rollout；
- 以 episode 总体结果为主要训练信号；
- 使用组内相对优势，不需要单独训练 value model；
- 通过 LoRA/QLoRA 更新模型；
- 工具执行、格式、任务完成和错误等信号被聚合到轨迹级 reward；
- 当前 trainer 没有真正保存并使用每个工具动作的 token span 和局部 advantage。

### 2.3 之前 GRPO 使用的规则 reward

之前的实验并不是用 gold tool sequence 直接给分，而是使用 rollout 中可观察的规则信号。这里需要区分**在线真实工具 reward**和**早期离线单动作 reward**。

#### 2.3.1 在线真实工具 GRPO reward

真实工具 online GRPO 在每次工具调用后记录一个 step reward：

| 工具执行状态 | 基础分 | 额外规则 |
|---|---:|---|
| `success` | +0.35 | 如果 observation 中包含 artifact、输出路径或常见文件后缀，再加 +0.15，单步最高 +0.60 |
| `empty` | -0.20 | 输出为空或没有有效结果 |
| `error` | -0.60 | 工具异常、超时、参数错误、文件不存在等 |

但是，训练时真正送给 GRPO 的主要是 episode-level reward，而不是简单把 step reward 直接相加。对一条包含 \(N\) 次工具调用的轨迹，当前规则可以概括为：

\[
R = -0.15
  + 0.95\frac{N_{success}}{N}
  - 0.45N_{error}
  - 0.20N_{empty}
  + \min(0.20, 0.05N_{artifact})
  - P_{long}
  - P_{turn}
  - P_{token}.
\]

其中：

- 如果没有任何工具调用，直接给 \(R=-1.0\)，防止模型学会不调用工具、直接结束；
- \(N_{success}/N\) 是工具成功率；
- 每个 error 工具调用额外扣 0.45；
- 每个 empty 输出额外扣 0.20；
- 有效 artifact 产出最多提供 0.20 的奖励；
- 当工具调用超过 8 次时，额外惩罚最多 0.30；
- 当轮数超过 14 时额外扣 0.10；
- response token 越长，最多额外扣 0.10；
- 最终 reward 被截断到 \([-1,1]\)。

用伪代码表示就是：

```text
if 没有工具调用:
    reward = -1.0
else:
    reward = -0.15
    reward += 0.95 * 工具成功率
    reward -= 0.45 * 错误调用数
    reward -= 0.20 * 空输出数
    reward += min(0.20, 0.05 * artifact数量)
    reward -= 长轨迹惩罚
    reward -= 超过14轮惩罚
    reward -= 长输出惩罚
    reward = clip(reward, -1, 1)
```

这套 reward 的优点是完全不需要 `expected_tools` 或 gold answer；缺点是它主要衡量：

- 工具能不能执行；
- 工具是否返回非空结果；
- 是否产生 artifact；
- 是否错误太多、调用太长。

它**没有直接判断**：

- 工具是否是任务语义上最合适的工具；
- 是否漏掉了任务所需的后续工具；
- 当前产物是否绑定了正确的对象、时间或图层；
- 最终工具链是否与 OEA gold sequence 一致。

这正是 Pure GRPO 出现“reward 较高，但正式 OEA Tool F1 和 exact sequence 不高”的主要原因之一。

#### 2.3.2 早期离线/单动作规则 reward

项目早期还有一条不执行真实工具的离线诊断链路。它只对模型输出的 JSON tool action 打分，规则如下：

1. 无法解析出完整 JSON tool action：直接得分 \(-1.0\)；
2. 统计工具名合法性 `valid_tools`；
3. 按工具 schema 统计必填参数和参数类型完整度 `arg_score`；
4. 只允许一个 action，多个 action 的 `action_count_score=0`，并额外惩罚多余 action；
5. 对重复工具调用计算 repetition penalty；
6. 对高风险经验计算 risk penalty；
7. 最终分数截断到 \([-1,1]\)。

纯 schema baseline 的组合为：

\[
R_{offline}=2(0.45V+0.35A+0.20C-P)-1,
\]

其中：

- \(V\)：工具名是否合法；
- \(A\)：参数是否满足 schema；
- \(C\)：是否符合单 action 约束；
- \(P\)：重复、高风险和额外 action 惩罚。

如果启用 ExperienceEvo reward prior，则组合改为：

\[
R_{offline}=2(0.25V+0.20A+0.40E+0.15C-P)-1,
\]

其中 \(E\) 是工具动作与 rollout-derived ExperienceEvo 推荐策略的匹配度，主要由经验质量 \(q\)、支持次数 \(n\) 和风险 \(risk\) 计算。

这条离线 reward 不能当作真实工具任务完成 reward。它只能说明模型是否能输出可解析、合法、schema-compatible 的 action。早期诊断中就出现过：模型只输出第一个合法工具，但没有继续完成后续步骤，却仍然得到较高 reward。

因此：

```text
早期离线 reward：格式/工具合法性诊断
在线 episode reward：真实工具执行状态诊断
正式 OEA 指标：事后 gold-based 工具链评测
```

三者用途不同，不能混合到同一张结果表中。

### 2.4 当前实验结果定位

已有完整 OEA eval 的关键结果为：

| 实验 | Success | Set F1 | Tool error |
|---|---:|---:|---:|
| Qwen2.5-3B Base | 71.86% | 0.5142 | 48.45% |
| Pure GRPO checkpoint-1900 | 70.65% | 0.5102 | 49.74% |
| Pure GRPO + ExperienceEvo v4-clean | 73.75% | 0.5137 | 34.17% |

这些结果说明：

- Pure GRPO 本身没有稳定超过 Base；
- 经验注入可以降低工具错误并提高成功率；
- 当前不能把 Pure GRPO 结果写成“RL 已经显著提升模型能力”；
- 更准确的表述是：完成了真实工具环境中的标准 GRPO 训练与 ExperienceEvo 运行时增强对照。

### 2.5 标准 GRPO 的主要问题

标准 GRPO 可能出现以下现象：

- 一次工具调用错误导致整条轨迹共同受到惩罚；
- 前面正确的动作和后面错误的动作共享相同 advantage；
- 工具执行成功但产物绑定错误时，reward 可能仍然偏高；
- 漏掉一个关键工具和多调用一个工具，未必得到足够强的差异信号；
- 模型不容易知道到底是哪一步导致最终失败。

## 3. 当前设计：产物来源感知 GRPO

### 3.1 解决的问题

地理空间任务中经常出现：

```text
工具执行成功
  ≠ 输入产物绑定正确
  ≠ 输出产物适合后续任务
```

例如用户要求分析灾后建筑变化，模型可能成功调用分割工具，但错误地使用了灾前影像。工具没有报错，普通执行奖励可能为正，但整个任务语义已经被破坏。

### 3.2 方法流程

当前设计的方法在标准 GRPO 前增加产物级审计：

```text
采样多条完整 rollout
  -> 记录每次工具调用的 action span
  -> 建立输入产物到输出产物的依赖图
  -> 检查来源、对象、时间、单位、CRS 和输出契约
  -> 检查产物是否被后续步骤正确消费
  -> 计算每个工具动作的局部信用
  -> 将局部信用对齐到对应 assistant token
  -> 与 episode advantage 一起更新 LoRA
```

对第 \(t\) 个工具动作，可以定义一个局部信用：

\[
c_{i,t}=w_sS_{i,t}+w_oO_{i,t}+w_pP_{i,t}-w_nN_{i,t},
\]

其中：

- \(S\)：输入产物来源是否正确；
- \(O\)：输出是否满足工具契约；
- \(P\)：输出是否被后续步骤正确消费；
- \(N\)：错误绑定、无效重复、空输出和负迁移惩罚。

最终不再让所有 assistant token 共享完全相同的优势，而是构造：

\[
\widetilde A_{i,t}
=(1-\lambda c_{i,t})A_i
+\lambda c_{i,t}D_{i,t},
\]

其中 \(A_i\) 是整条轨迹的 GRPO 优势，\(D_{i,t}\) 是同一产物前缀下候选动作的局部相对收益。

### 3.3 用小白能理解的话说

标准 GRPO 像老师只看一篇完整作文，最后给一个总分：

```text
整篇作文：80 分
```

如果作文中间有一句关键错误，老师只告诉你“整篇还不错”，模型不容易知道具体哪一句需要改。

当前方法像老师除了给总分，还会在句子层面标注：

```text
第 1 个工具调用：正确
第 2 个产物绑定：错误
第 3 个下游消费：正确
```

这样模型不仅知道“这条轨迹整体好不好”，还知道“哪一次工具调用值得保留，哪一次绑定需要避免”。

### 3.4 它不是简单的步骤奖励

如果只是把每一步的分数加起来，再得到一个总 reward，仍然是普通 GRPO 的 reward shaping。

只有完成以下链路，才是当前设计的方法：

```text
识别工具动作边界
  -> 建立产物依赖
  -> 验证来源和下游消费
  -> 得到局部信用
  -> 对齐到对应工具 token
  -> 进行动作级优势更新
```

因此，当前方法的潜在贡献不是“首次提出 step reward”，而是：

> 将地理空间工具任务中的产物来源、语义绑定和下游消费证据，接入 Agentic RL 的动作级信用分配。

## 4. 两种方法的直接对比

| 项目 | 已完成的标准 GRPO | 当前设计的产物来源感知 GRPO |
|---|---|---|
| RL 类型 | on-policy policy gradient | on-policy policy gradient |
| 组内采样 | 有 | 有 |
| 总体 episode reward | 有 | 保留 |
| 优势粒度 | 整条轨迹 | 整条轨迹 + 工具动作 |
| 产物依赖图 | 未接入 trainer | 核心组件 |
| 输入来源检查 | 主要作为运行时/最终结果信号 | 显式参与局部信用 |
| 下游消费检查 | 非动作级 | 对应到工具动作 |
| Token 对齐 | 共享 episode advantage | 对应 action span 的局部 advantage |
| 是否已经完成 | 是 | 否，仍是设计和开发阶段 |
| 适合的简历表述 | “完成标准 GRPO 训练与真实工具闭环” | “设计/实现产物来源感知信用分配” |

## 5. 与 ExperienceEvo 的关系

二者不是互相替代，而是两个层次：

```text
ExperienceEvo：推理时复用什么经验？
产物来源感知 GRPO：哪些工具动作值得被策略强化？
```

ExperienceEvo 负责：

- 从真实 rollout 抽取产物状态转移经验；
- 根据当前状态检索经验；
- 检查经验适用边界；
- 在推理时注入经验或回退 ReAct。

产物来源感知 GRPO 负责：

- 观察当前 rollout 中的工具动作；
- 判断产物来源和消费是否可靠；
- 将信用分配给具体工具调用；
- 让模型逐渐内化正确的工具使用行为。

因此可以组合成：

```text
ExperienceEvo 经验检索
  -> 引导 rollout
  -> 产物来源审计
  -> 动作级信用分配
  -> GRPO 更新策略
```

但需要单独做消融，不能一开始把所有机制同时打开。

## 6. 两个版本的简历写法

### 6.1 已完成的标准 GRPO：推荐写法

> **真实工具环境中的 Agentic GRPO 训练：**基于 veRL/Swift 构建 Qwen2.5-3B 的 online GRPO 训练闭环，在真实 OpenEarth 工具环境中采样多轮任务轨迹，采用组内相对优势更新 LoRA/QLoRA，并完成固定 OEA 测试集上的 Base、Pure GRPO 和 ExperienceEvo 增强对照评测。

这个版本强调的是已经做过的工程和实验事实，不夸大效果。

### 6.2 如果只想突出算法感：标准 GRPO 短版

> **Agentic GRPO 训练闭环：**针对多轮地理空间工具任务，搭建真实工具 rollout、组内相对优势计算和 LoRA/QLoRA 更新流程，支持断点续跑、工具错误记录和固定 OEA manifest 的端到端评测。

### 6.3 当前设计的产物来源感知 GRPO：尚未完成实验时

> **设计产物来源感知的 Agentic RL：**针对工具执行成功但文件、图层、对象或时间状态绑定错误难以归因的问题，构建产物依赖图，联合校验输入来源、输出契约和下游消费关系，将局部信用对齐至对应工具调用 token，改进 GRPO 的长链路信用分配。

### 6.4 完成实现和消融后可使用的版本

> **产物来源感知 GRPO：**在标准 GRPO 的组内优势之外，引入文件/图层/对象/时间/单位等产物语义绑定检查，计算工具动作级局部优势并对齐至对应 assistant token；通过标准 GRPO、过程奖励和动作级信用分配消融，验证多步工具链的绑定准确性、错误恢复和未见产物组合泛化。

## 7. 简历中不要混写的内容

以下两种表述容易造成事实错误：

1. 把当前已经完成的 Pure GRPO 写成“产物来源感知 GRPO 已经验证”；
2. 把 ExperienceEvo Boundary v1 的运行时经验过滤写成“RL 学会了经验边界”。

目前最准确的项目结构写法是：

```text
已完成：真实工具环境中的标准 GRPO + ExperienceEvo 运行时增强
正在设计：产物来源感知的动作级信用分配 GRPO
```

## 8. 推荐最终版本

如果简历只能留一条，建议使用下面这条：

> **地理空间 Agent 的真实工具 RL 与经验增强：**基于真实 OpenEarth 工具环境搭建 Qwen2.5-3B online GRPO 训练闭环，采用组内相对优势更新 LoRA/QLoRA，并结合 ExperienceEvo 进行产物状态转移经验检索；进一步设计产物来源感知的动作级信用分配机制，校验文件/图层/时间等语义绑定并将局部优势对齐至工具调用 token，缓解长链路工具任务中的错误归因问题。

这条写法把“已完成部分”和“设计中的创新部分”放在同一条主线中，但没有把尚未完成的算法写成已有实验结论。
