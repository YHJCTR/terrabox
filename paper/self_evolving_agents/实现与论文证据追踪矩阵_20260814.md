# 实现与论文证据追踪矩阵

本文档是 `ExperienceEvo` 与 `PromptEvo` 投稿前的实现边界、证据来源和结论强度控制表。它不是实验结果，也不替代逐任务原始记录。每次修改实现、实验协议、主文或补充材料时，应先更新本表，再同步相关论文和证据包。

## 使用规则

本表将陈述分成三类：

- **实现事实**：可以直接由当前仓库代码、静态配置或已有原始文件核对。
- **投稿协议**：论文要求正式实验遵守的设计，但当前代码可能尚未强制执行。
- **最终证据**：只有在冻结 manifest、任务级记录和统计审计完成后，才能填入主表并写入摘要或结论。

“实现事实”不自动等于“方法有效”；“投稿协议”不自动等于“当前程序已经实现”；“历史诊断”不自动等于“因果结果”。论文中使用过去时描述的数字必须能回链到最终证据包，不能只回链到汇总报告。

### ExperienceEvo 的最小可解释链

每个 test task 的审计记录应能回答以下问题：

1. 当前状态是否存在兼容的 learned family？
2. 是否存在 deterministic fallback？如果存在，是否优先返回并抑制 learned ranking？
3. 返回的 family provenance 是 train rollout 还是 runtime fallback？
4. agent 是否选择推荐的 tool policy？
5. 选中的参数是否绑定当前运行中真实返回的 artifact/reference？
6. 观察是否创建有效 target product，且该 product 是否进入最终请求的 answer/artifact？

只有第 1--6 项都能从同一任务的逐步日志和 manifest 中重建，论文才可以把机制分析写成结果；否则只能写成设计目标或实现审计。

## PromptEvo

| 论文陈述或实验对象 | 当前实现状态 | 权威核验位置 | 正式实验必须保存 | 允许的结论范围 |
|---|---|---|---|---|
| paired diagnosis | 已实现接口，使用 prompt diff、共同 task IDs 和 paired traces 的输入契约 | `promptevo/loop.py`、`contrastive_optimizer.py` | parent/candidate fingerprint、literal diff、paired task hash、trace batch IDs | 可以描述 diff-grounded proposal；不能把诊断当作因果估计 |
| typed patch kinds | 已实现 `tool_selection`、`argument_validation`、`error_recovery`、`termination_and_repetition` | `promptevo/protocol_patch.py` | patch JSON、kind、trigger、rule、scope、priority、risk | 可以报告结构化协议更新；不能由 schema 合法推出安全或泛化 |
| compiler validation | 已实现字段、范围、重复/冲突、任务特定字符串、placeholder、dynamic anchor 和 high-risk withholding 检查 | `protocol_patch.py` `validate_patches()` / `compile_protocol_prompt()` | compiler version、errors、warnings、compiled fingerprint、人工抽查 | 编译成功只代表静态检查通过 |
| patch evidence | 当前只规范化字符串列表；空 evidence 合法，不解析到 trace/attribution | `protocol_patch.py` `_as_patch()` | patch-level declared evidence、trace/attribution IDs、resolution status、resolution errors | 当前只能称 declared evidence，不能称 trace-backed evidence |
| candidate ranking | 当前 `_score` 使用 `success_rate + 0.5 * tool_f1` 选择候选 | `promptevo/loop.py` | 全部候选、排序、候选指标、未 rollout 原因 | 可以报告内部候选排序规则；不能将排序本身当作接受门 |
| empirical acceptance | 当前 updater 的实际接受条件是 success-rate tolerance，并要求 runner/dev IDs；未强制论文中的 protected-metric conjunction | `promptevo/loop.py` | primary/protected metric、threshold、每个拒绝原因、dev split hash | 在协议闭合前不能声称安全非退化接受 |
| `run.py accept` | 当前命令可把 proposal 写成 prompt 文件，但不检查 dev acceptance、ledger 或 locked test | `promptevo/run.py` `_cmd_accept` | persisted candidate fingerprint 与 dev decision 的绑定 | 保存文件只能称 persisted candidate，不能称 accepted prompt |
| no-update control | 属于正式实验要求，不是 compiler 自动保证 | 论文实验协议、证据模板 | 与每个演化条件相同的 actor/tool/evaluator/failure policy | 没有 no-update control 时，不能排除服务/随机性变化 |
| locked test | 属于正式实验要求；候选搜索必须在 dev 完成后冻结 | 论文实验协议、证据模板 | test split hash、selected fingerprint、一次性 test run、selection timestamp | 只能对冻结 candidate 报 test 结果 |
| cross-environment transfer | 属于待验证研究问题，不是静态规则的先验性质 | PromptEvo 主文 transfer protocol | source/target interface diff、disjoint split、未修改 prompt fingerprint | 未完成前不得写“跨环境泛化” |

### PromptEvo 的候选生命周期

正式运行应保留完整的不可覆盖链：

`parent prompt -> paired diagnosis -> candidate pool -> compiler/evidence audit -> frozen dev rollout -> acceptance decision -> locked test`。

- 编译拒绝、evidence unresolved、没有 runner、没有 dev task、dev 失败和 protected metric 违反者都必须进入 ledger；
- 只有所有预声明门槛通过的 candidate 才能被标为 `accepted`；
- 没有被 dev 接受的 proposal 可以保存供分析，但必须标为 `persisted candidate`；
- test 结果不得回写 candidate、threshold、patch 或 prompt；
- candidate 数量、候选排序和重试政策都属于统计对象，不能只保留最终最好的一条。

## 共同的结果填表规则

### 主表数字的来源优先级

1. 逐任务 `task_metrics.jsonl` 和原始结果 hash；
2. 与条件匹配的 immutable manifest；
3. 共同 task IDs 的 paired comparison；
4. 预先固定重采样方案得到的 confidence interval；
5. `tables_for_paper.csv` 作为最终排版输入。

`report.json`、历史实验汇总、单次小样本诊断和人工挑选案例只能用于交叉核验、错误分析或实验设计，不能直接填入主结果表。

### 结果解释限制

当 success 上升但 ordinary answer 不变时，应分别报告，不能写成总体能力提升。当 tool F1 上升但 requested artifact completion 下降时，应报告 trade-off，不能写成部分成功。当 cost、latency、tool calls 上升时，应在同一表或补充材料中保留。基础设施失败、evaluator error、empty final 和 retry exhaustion 应有固定分母规则，不能按条件选择性删除。

### 两篇论文共同的投稿门槛

- 主表不存在 `TBD`；
- 每个 baseline 标注 official、adapted 或 reimplemented，并说明接口差异；
- 主比较共享 split、actor、tool manifest、prompt/dynamic-context fingerprint、cache/retry/failure policy；
- 至少有一个 no-update 或等价 schedule control；
- 关键指标有配对不确定性区间；
- actor 与 judge 同源时有 independent judge 或人工盲审子集；
- 经验 provenance 与 prompt candidate ledger 可审计；
- 论文、补充材料、证据包和代码中的术语一致；
- 完成 Overleaf PDF 编译、图表视觉检查、作者信息、引用元数据、隐私和许可证检查。
