# 实验前审稿备忘录

审稿对象：`experienceevo_v4/main.tex` 与 `promptevo/main.tex`。
审稿阶段：developmental / pre-experiment。
审稿范围：方法合理性、证据边界、实验设计、可复现性和投稿风险；本次不审任何尚未完成的实验结果。

## 总评

两份稿件应该保持独立投稿线。

- `ExperienceEvo v4` 的方法创新在于以“当前已验证产物状态 -> 下一目标产物状态”为最小可迁移单元，并在运行时按状态触发检索。它与 episodic memory、自然语言 reflection 或完整 workflow skill 有可辨识的表示差异。
- `PromptEvo` 的方法创新在于从配对 rollout 进行 prompt-diff 归因，并将静态协议补丁限制为可编译、可拒绝、可通过真实 dev rollout 接受的对象。它不是经验库或 runtime memory。

当前稿件已扩展为完整的 arXiv 风格方法初稿：包含相关工作、正式问题定义、实现对齐的方法细节、实验与审计协议、初步/负结果和附录。它们仍不应称为 `final` 或 `submission ready`。ExperienceEvo 的已有数字被明确限制为单配置诊断；PromptEvo 的已有跨环境数字被明确保留为混合/负结果，不能在摘要或结论中改写为普适提升。

## 主要问题

### S1: 两张主结果表仍为 `TBD`，因此当前不是可上传版本

`experienceevo_v4/main.tex:187--205` 与 `promptevo/main.tex:197--213` 的主比较表均保留空白结果。这在实验前稿中是正确做法，但 arXiv 论文不能以占位表、计划中的 CI 或待定 baseline fidelity 作为核心证据。历史诊断表只能保留为开发记录，不能替代最终主表。

投稿前必须：以固定 manifest 跑出全部主表行，给每行填写任务数、结果、资源指标和 baseline fidelity；附上任务级结果、配对不确定性区间和失败计数。替换主表后，应同步重写摘要、结果段、讨论和结论，确保每项数字均可在公开或可审计的运行记录中定位。

### S1: ExperienceEvo 的现有全量比较尚未证明配置可比

`experienceevo_v4/main.tex:238--260` 报告 base/v4 的 1,162 任务历史数值，但同一段已说明它们不是冻结的因果比较。仅有相同任务数和表面 actor 名称不足以排除 tool registry、prompt、缓存、provider、retry、服务版本、store source 或生成类评分口径变化。已核对的两份 `report.json` 还显示 workers 分别为 4 和 3，且导出的 unique-tool inventories 并不完全相同；这进一步排除了将其当作直接因果对比的可能。`main.tex:185--214` 已正确规定最终 manifest 规则，但该规则还未对历史表逐字段兑现。

投稿前必须：为每个比较输出并对照 manifest diff；若任何字段不一致，则将其拆为不可直接比较的开发日志。最终论文只使用同任务 ID、同工具/模型/重试策略下的配对运行，并保留原始失败和重跑记录。

### S1: ExperienceEvo v4 继承的 runtime fallback 与 train-rollout 经验未被当前结果分离

`src/terrabox/evolution/experience_evo/v3/runtime.py:931--937` 在 fallback 规则命中时直接返回 `v3_fallback_*` families；v4 继承这一 `retrieve()` 路径。它们来自当前任务形状和工具契约，不是由 train rollouts 构建的 transition family。若历史结果没有逐步记录 family provenance，不能把全部收益归因于经验库或 Quse。

投稿前必须：在 trace 中记录每个候选的 provenance，分别报告 learned-family coverage、fallback coverage、推荐命中和成功翻转；至少加入 learned-store-only、fallback-only/generic-guard-only 以及 full v4 对照。否则论文应把贡献范围写成“product-state guidance runtime”，而不能写成纯粹的 train-rollout experience transfer。

### S1: v4 将 runtime fallback 误写为 rollout-derived lesson，且现有 trace 缺少 family provenance

`src/terrabox/evolution/experience_evo/v4/runtime.py:126--153` 对所有检索结果注入 “Retrieved lessons are rollout-derived product-state transitions” 的通用语句，但其继承的 `v3/runtime.py:931--937` 会在 fallback 命中时直接返回 deterministic `v3_fallback_*` family。v3 的初始指导文本会明确提及 runtime fallback，而 v4 的对应文本没有这一限定。该问题会把工程 heuristic 表述为离线经验，属于方法透明性问题，不是文案细节。

进一步，`src/terrabox/agent/eval_modes/common.py:220--231` 的 `evolution_trace` 目前只保存 product state、recommendation-level tool 信息和后续选择/阻断状态；它不保存 retrieved family ID、family provenance 或 fallback 命中。因此历史结果不能在事后重建 learned/fallback 覆盖率，也不能支撑“经验被使用”的归因分析。

投稿前必须：修正 v4 注入文本，在实际提示中显式区分 train-rollout family 和 runtime fallback；在每次 retrieval 的 trace 记录 family ID、`provenance_summary.source`、检索排序与所用 policy；冻结该实现后重跑最终比较。旧历史结果仍可作为无 provenance 的开发诊断保留，但不得用于 learned experience transfer 的机制结论。

### S1: PromptEvo 尚无一次与现有 typed-patch 接受机制一致的完整实证

`promptevo/main.tex:223--251` 明确说历史 Stage 版本可能早于或不同于当前 compiler + frozen-dev 接受路径；因此这些数字不能验证论文的主方法。`main.tex:166--173` 的接受定义、`main.tex:197--221` 的锁定测试主表，以及 `main.tex:261--273` 的算法叙述目前是正确的 protocol，但尚不是结果。

投稿前必须：在每个拟保留的环境完成一次候选池、编译拒绝、固定 dev 接受和唯一锁定 test 的完整链路；发布 candidate ledger 和 no-update schedule control。没有这套证据，论文应收缩为系统设计/预注册，而不是“prompt evolution”效果论文。

### S1: PromptEvo 的论文接受公式与当前执行接受门不一致

`promptevo/main.tex:166--173` 要求 primary metric 与所有 protected metrics 同时过门；但 `src/terrabox/evolution/promptevo/loop.py:93--115` 当前先以 `success_rate + 0.5 * tool_f1` 选取候选，再只用 `success_rate` 的容差决定 `accepted`。因此，一个损害安全、成本、工具可靠性或其他受保护维度的候选，仍可能在当前代码中被接受。论文不能把未执行的多指标协议当成实际实现保证。

投稿前必须二选一：将运行时接受逻辑扩展为对每个声明 protected metric、方向和容差的显式检查并记录逐项拒绝原因；或者把论文缩写为当前单主指标接受门，并删除所有“保护维度由接受门保证”的表述。前一种才支持安全/非退化论文主张，且新逻辑必须在冻结实验中实际使用。

### S1: PromptEvo 当前的 patch evidence 字段可为空，且编译器不验证其 trace 归属

`src/terrabox/evolution/promptevo/contrastive_optimizer.py:500--514` 会将归因 evidence 放入 typed-patch 候选生成提示词，但 `src/terrabox/evolution/promptevo/protocol_patch.py:84--96` 对返回的 `evidence` 仅执行字符串列表规范化：字段缺失时默认 `[]`，没有非空要求，也不检查某条 evidence 是否引用真实 trace、attribution 或诊断批次。故当前代码能说明候选*可声明* evidence，不能说明每个补丁都是 trace-backed，也不能在发布后回溯补丁与观察之间的关系。

投稿前必须：在 candidate-ledger/runner 层为每个进入 dev 的 typed patch 强制非空 evidence，并将每条 evidence 解析到版本化的 trace 或 attribution ID；保存解析成功/失败状态、脱敏 ID 映射和人工抽查。无法实现时，论文不得使用 “trace-backed patch” 或“每个更新均有证据”的强表述，应把方法收缩为 evidence-prompted candidate generation。

### S1: ExperienceEvo 的经验库因果贡献尚未隔离

当前 v4 包含状态检索、Quse 排序、soft verifier，以及两类窄口径 schema/path 保护。没有 `no-store soft-only` 与 `generic-guard only` 对照时，无法证明收益来自产物状态经验而不是通用运行时工程修复。

投稿前必须：在同一固定 subset 和完整 test 上至少补齐 `base + generic guard`、`no-store soft-only`、`full v4`；三者使用同一 agent、prompt、工具可见性、重试策略和资源配置。

### S1: PromptEvo 的静态候选不能代替真实验证

源码中没有 `RolloutRunner` 或固定 `dev_task_ids` 时会明确返回 `accepted=False`。任何基于历史轨迹或静态评分挑出的候选都只能称作 candidate，不得写成 “improved prompt”。

投稿前必须：固定 development 集和 protected metrics；保存每个候选的 prompt fingerprint、真实 rollout、接受门阈值、被拒绝原因和最终一次锁定 test。

另需注意入口边界：`src/terrabox/evolution/promptevo/run.py:184--218` 的独立 `accept` 子命令会将 proposal JSON 的 `compiled_prompt` 或 `revised_prompt` 写入版本文件，但不检查 `ContrastiveUpdater.update()` 的 dev decision。它只能理解为候选持久化，不是经验接受。最终 test manifest 必须以实际加载的 prompt fingerprint 回链到 candidate ledger 中的 frozen-dev accepted row；无法回链的 CLI 文件不得进入主结果。

### S1: 两篇论文都缺少泛化证据

ExperienceEvo 不能从单一 OEA/单一 actor 模型推出跨工具环境结论。PromptEvo 如要主张通用静态协议，必须在至少两个接口差异明显的环境中按同一接受门验证，不能只在同一 benchmark 的多个阶段上比较。

投稿前必须：至少增加模型/种子复验和第二环境；若资源不足，应在标题、摘要和结论中把范围限定为 `OpenEarthAgent-style geospatial workflows` 或具体接口，而不是 general LLM agents。

### S1: Judge 与 actor 同源会削弱答案结论

若 rollout actor 和 LLM answer judge 使用同一 provider/model family，普通 answer accuracy 的结论有偏好风险。生成类任务的最后工具/产物成功指标与文本答案正确率也不是同一指标。

投稿前必须：报告 judge prompt、缓存、失败重试和错误样本；对一部分样本加入独立 judge 或盲审人工复核；将 artifact completion 和 ordinary answer accuracy 分表报告。

### S2: PromptEvo 的归因应明确为证据约束的假设，不是因果证明

配对轨迹降低了任务难度差异，但仍不能排除模型随机性、工具状态和未观测上下文。文中应持续使用 `attribution hypothesis`、`associated with` 等限定语，并报告 unexplained metric movement。

### S2: 参考文献需要在投稿前做 venue 级核验

当前稿件引用了原始论文和本地 PDF 中可核验的近期工作，但手工 `thebibliography` 尚未替换为目标 venue 的统一 BibTeX 样式。本轮已更正 ToolLLM、ToolRL、API-Bank、tau-bench 和 GEPA 的手写首作者/venue 信息；尤其是 2025--2026 arXiv 工作的作者列表、版本号、最终出版 venue 与标题大小写仍可能更新。

投稿前必须：根据目标会议模板和论文官方页面逐条重新导出 BibTeX；保留 arXiv ID；不得把 adapted baseline 的实现论文引用写成官方复现事实。

### S2: ExperienceEvo 的状态词表和 artifact tracker 需正式定义

目前实现中的状态类型、成功 observation 判定、multi-target 重复产物、fallback 规则和失败 observation 截断，都会影响检索和最终结论。主文至少应给出状态词表类别和状态更新伪代码；完整规则放 supplement。

### S2: 第三方 baseline 复刻口径必须透明

Reflection、MemRL、ExpeL 等若因 OEA 接口而采用 adapted/reimplemented 版本，主表必须直接标记，并给出 official source、commit、保留/替换的机制和不适配原因。不能将接口适配结果表述为无差异官方复现。

## 优先实验清单

1. ExperienceEvo：`generic-guard only`、`no-store soft-only`、full v4 的固定 200 条 smoke 和全量验证。
2. ExperienceEvo：full v4 的 `step hint off`、`Quse off`、`verifier off` 同种子/同任务配对分析；补推荐命中、实际选择、成功翻转和失败反例审计。
3. PromptEvo：每个环境一次 frozen dev acceptance + 一次 locked test；不要反复用 test 集搜索 Stage2。
4. 两篇共同：主指标的 paired bootstrap CI、任务级结果文件覆盖率、transient/infrastructure error 报告。
5. 两篇共同：第二模型或第二工具环境，以及独立答案核验子集。
