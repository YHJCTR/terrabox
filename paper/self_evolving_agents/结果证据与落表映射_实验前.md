# 自进化 Agent 结果证据与落表映射

本文档连接当前已经存在的 rollout 产物、两份论文主稿中的表格字段，以及最终投稿证据包。它只描述截至 2026-08-13 已可定位的记录与其使用边界，**不把历史诊断重标为最终比较结果**。最终发布时，以 `投稿证据包模板.md` 规定的冻结 manifest、任务级记录和统计结果为准。

## 1. 当前可定位的 ExperienceEvo 历史产物

下列两组结果均使用 `data/oea_full_sft/openearth_test_tasks.json`，且报告任务数均为 1,162：

| 条件 | 原始目录 | 创建时间 | `workers` | Success | 平均 Tool F1 | tokens 总数 | 说明 |
|---|---|---|---:|---:|---:|---:|---|
| Base | `tmp/trajectories/longcat_base_current_code_eval_20260805/standard/` | 2026-08-05 | 4 | 0.8554 | 0.6923 | 64,488,967 | 现有基线诊断 |
| v4 | `tmp/trajectories/experience_evo_v4_oea_train2000_longcat_eval_20260807a/standard/` | 2026-08-07 | 3 | 0.9105 | 0.7635 | 60,883,562 | 现有 v4 诊断 |

两份 `report.json` 都是从各自 `results/<task_id>.json` 派生，并且给出了 filter setting、工具清单、状态分布和 LongCat answer judge 汇总。因此它们适合用于：核验历史轨迹是否存在、复现历史描述性表格、选取失败案例、设计消融与估算后续资源需求。

它们**不适合**用于 ExperienceEvo 主表中的因果或显著性比较，原因如下：

1. 两个条件的 worker 数不同（4 对 3），且报告导出的 `unique_tools_called` 并不完全一致。
2. 现有 `report.json` 没有冻结的 code commit/dirty-tree digest、prompt fingerprint、完整 tool schema hash、模型请求参数、服务镜像摘要、缓存策略版本或逐条件的 retry/timeout manifest。
3. v4 会继承 `experience_evo_v3_runtime_fallback`；历史 `evolution_trace` 未逐步保存检索 family ID 与 provenance，因而无法回溯“收益来自 learned family”还是 runtime fallback。
4. 两组 answer judge 汇总均使用 LongCat，且普通 answer accuracy 与 generated-artifact completion 是不同口径，不能合成一个“答案分数”。

因此，`experienceevo_v4/main.tex` 中的 diagnostic table 可以保留这些数字及其限制，但其 `tab:main` 必须继续保持空白，直到在同一冻结 manifest 下重跑全部条件。

## 2. 当前 PromptEvo 历史产物与用途

`src/terrabox/evolution/promptevo/实验结果汇总.md` 汇总了已有的三类 broad-stage 记录：

| 环境 | 样本量 | 历史方向 | 可用结论 | 不能得出的结论 |
|---|---:|---|---|---|
| `tau2-bench`, Qwen3 8B | 1,500 | success/tool F1 8.47% 到 9.20%，调用和耗时上升 | 存在成本-效用权衡和 domain heterogeneity | 当前 typed patch 被冻结 dev gate 接受且泛化 |
| AgentDojo, Qwen3 8B | 1,081 | Stage 2 success 轻微下降，安全指标近似持平 | 没有稳定的广泛改进证据 | 提示词演化提高安全或 utility |
| OpenEarthAgent, LongCat think | 1,162 | success 从 86.1% 降至 83.3%，部分工具序列指标局部变化 | 负结果应保留 | Stage 2 修复 Stage 1 或静态协议普适有效 |

这些阶段性实验可能早于当前的 typed-patch compiler、patch evidence 审计和 frozen development acceptance 协议。因此它们只对应 `promptevo/main.tex` 的 `tab:diagnostics`，不能填入 `tab:main`，也不能作为 abstract 的效果数字。

特别地，当前 `ContrastiveUpdater.update()` 的真实代码路径先以 `success_rate + 0.5 * tool_f1` 排序候选，再仅以 success 容差决定 `accepted`。它还不等价于论文提出的多 protected-metric 接受门。最终实验应么实现该门并记录每个维度的拒绝原因，么将主稿严格缩写为当前单指标门；两种表述不可混用。

## 3. 从 `results/` 到主表的字段映射

OEA rollout 的权威输入是每任务一个的 `results/<task_id>.json`，不是汇总 `report.json`。`src/terrabox/evolution/shared/rollout_report.py` 可从任务记录计算大部分执行和工具指标；但最终投稿时应导出独立的、不可覆盖的 `task_metrics.jsonl`，而不是依赖临时汇总脚本的显示输出。

| 论文/证据包字段 | 优先来源 | 计算或审核要求 | 注意事项 |
|---|---|---|---|
| 任务分母、状态 | `results/<task_id>.json` + split manifest | 每个 planned task 一行，保留 completed/failed/empty final | 不能只对成功任务平均 |
| Success | 任务记录的 `success` | 报告点估计、共同任务配对差与 CI | 必须固定 evaluator 与 failure policy |
| Tool F1 | `expected_tools` 与实际重建 tool sequence | 使用版本化同一 scoring 实现 | `expected_tools` 只能用于评分，不能进入 ExperienceEvo runtime/store 或 PromptEvo patch 文本 |
| Ordinary answer | `judge_answers.py` 输出及 cache | 记录 judge provider/model、重试、cache 和独立/人工抽样 | 与 actor 同源时不可作为唯一质量证据 |
| Generated artifact | 最终工具/产物 contract 审计 | 单列 generated task 分母与完成定义 | 不得与 ordinary answer accuracy 混合 |
| Tokens/latency/调用 | 任务 `tokens`、`time`、tool history | actor token 与 optional verifier/checker token 分开 | worker 数与 cache 策略进入 manifest |
| Tool/infra error | tool observation、terminal status 与预定义 failure classifier | 分别报告 deterministic contract error 与 transient infrastructure error | 不能把超时静默删除 |

`report.json` 可用于交叉检查 aggregate 是否与任务级导出一致，但它不是 manifest，且字段会随不同 adapter/rebuild 版本变化。最终 `tables_for_paper.csv` 的每个单元格应回链到 `task_metrics.jsonl`、`paired_comparisons.csv` 和 `bootstrap_summary.json`。

## 4. ExperienceEvo v4 的最小主比较矩阵

不修改 v4 代码时也不能用历史全量 base/v4 数字替代下列对照。每一行应共享：test task hash、actor/model、prompt fingerprint、tool manifest、retry/timeout/cache、资源策略、answer judge 和 artifact contract。

| 条件 | Read-only learned store | v3 fallback | soft state guidance/verifier | image/calculator generic guard | 论文中能支持的比较 |
|---|---:|---:|---:|---:|---|
| Base | 否 | 否 | 否 | 否 | 未增强基线 |
| Base + generic guard | 否 | 否 | 否 | 是 | 通用工程保护的效果 |
| No-store soft-only | 否 | 否 | 是 | 明确固定 | 状态语言/soft verifier 的效果 |
| Learned-store-only | 是 | 否或独立开关 | 是 | 明确固定 | learned transition 的必要证据 |
| Fallback-only | 否 | 是 | 是或明确固定 | 明确固定 | inherited heuristic 的贡献 |
| Full v4 | 是 | 是 | 是 | 是 | 实际部署组合 |

当前 v3-inherited `retrieve()` 在 fallback 非空时会直接返回 fallback families，早于 ordinary learned-store ranking；它不是与 learned family 共同排序的轻微辅助规则。因此若无法单独关闭 fallback，必须从主张中删除“learned-store-only transfer”或在论文中将方法定位为 product-state guidance runtime。最终机制日志逐 step 至少要含：`learned_candidate_family_ids`、`retrieved_family_ids`、`family_provenance`、`fallback_priority_applied`、retrieval rank/score、recommended/selected tool、binding check、guard event、verifier status 和 product state。不得运行后仅凭 tool slug 反推 provenance。

## 5. PromptEvo 的最小接受与报告链

每一轮优化必须保存完整链：paired construction traces -> diagnosis -> candidate pool -> compiler/evidence audit -> frozen dev rollout -> one locked test。缺少任一环节时，输出只能叫 candidate 或 diagnostic。

1. **Construction**：冻结 paired diagnosis task IDs、原始/当前 prompt fingerprint、literal diff、actor/tool/evaluator manifest，以及 trace batch IDs。
2. **Typed patch evidence**：每个要进入 dev 的 patch 必须有非空 `declared_evidence`，并可解析到已留存的 trace 或 attribution ID；当前 compiler 本身不实现此验证，需在 candidate-ledger/runner 层实现并留存 `evidence_resolved`。
3. **Development acceptance**：在未使用过 final test 的固定 dev 集上，逐候选计算 primary 与所有预声明 protected metrics。记录所有 rejection，不只保存最优候选。
4. **Locked test**：仅对 accepted 且 fingerprint 已冻结的版本执行一次。test 不得反过来修改阈值、patch 或 prompt。
5. **No-update control**：按相同 trace collection、候选预算和评测调度执行，但不改部署 prompt；若它发生同等变化，不得将变化归给 prompt。

需要额外防止命令行持久化绕过证据链：`run.py accept` 可以把 compiler-valid proposal 写成命名 prompt 文件，但它不读取 `ContrastiveUpdater.update()` 的 `accepted` 状态，也不验证 dev/test 划分。该文件可以用于手工 rollout，却不是已接受版本。每个 test manifest 必须记录实际加载的 prompt fingerprint，并在 candidate ledger 中回链到对应的 completed dev decision；无法回链的版本不得进入 test，更不能称为 accepted/evolved prompt。

对 AgentDojo 或同类安全环境，表格至少分列 clean utility、attacked utility、security、attack success、runtime/tool error、calls、tokens 和 time。单一 balanced score 不能覆盖安全回归。

## 6. 填写主稿前的逐项核验

将任何数值写入两份 `main.tex` 的 `tab:main` 前，负责人应在对应 release evidence 目录确认：

- `manifest.json` 中的代码、模型、工具、prompt、资源和 evaluator 字段已完整，且对比条件间的允许差异已解释。
- `split_manifest.json` 证明 train/dev/test 无重叠，且最终 test 的使用次数为一次。
- `task_metrics.jsonl` 覆盖所有 planned tasks；`failure_accounting.json` 的分母与主表一致。
- `paired_comparisons.csv` 的共同 task ID 集合可复算，`bootstrap_summary.json` 中有预定义区间和随机种子。
- ExperienceEvo 具有 family provenance audit，并按 learned/fallback/no-family 分层。
- PromptEvo 具有包含编译拒绝、evidence 未解析拒绝、dev 拒绝和被送入 test 的完整 candidate ledger。
- baseline 标为 `official`、`adapted` 或 `reimplemented`，并明确代码来源/commit 和接口差异。
- Overleaf 已用目标 venue 模板编译；主稿/补充材料引用、图形、表格、匿名信息和链接经过人工检查。

完成上述核验后，才可以将主稿中的 `TBD` 替换为证据包中已审计的数字，并同步重写 abstract、results、discussion 和 conclusion，使其只陈述该证据真正支持的范围。
